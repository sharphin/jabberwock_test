# ベンチマーク（セルフホストjwc・Rust・C++・Goのみ）

## 一括コマンド

Linux / WSL2で、リポジトリ直下から実行する。Windowsネイティブも対応するが、Clang/LLVMとRust/Goのリンク環境が必要。

```sh
# 5種類の簡易計測（既定8反復）
python3 scripts/benchmark_report.py

# 全21種類 × 8回（4者比較。各言語が先頭を2回ずつ担当）
python3 scripts/benchmark_report.py --full

# 既存のセルフホストjwcを指定する場合（ブートストラップ省略）
python3 scripts/benchmark_report.py --full --jwc path/to/jwc

# 個別ケース・実行回数
python3 scripts/benchmark_report.py --cases fib sort --runs 7

# 同一環境・同一入力の過去結果と比較
python3 scripts/benchmark_report.py --full --baseline path/to/previous-benchmark-report.json
```

Windows（PowerShell、構築済みjwcを指定する場合）:

```powershell
.\scripts\benchmark_windows.cmd --full --jwc .\target\release\jwc-local.exe
# Visual Studio/Clang x64環境が初期化済みの場合は直接でも可
py scripts/benchmark_report.py --full --jwc .\target\release\jwc-local.exe
```

`benchmark_windows.cmd` はWindows x64のVisual Studio環境を初期化し、
Clang、Rust、Go、Pythonの存在を確認してから `py -3` でベンチマークを起動する。
GitHub Actionsは使用しない。

Windowsでは実行時間を`perf_counter`、メモリをWindows APIの`PeakWorkingSetSize`で計測する。
Linuxの`wait4`最大RSSとWindowsのピークワーキングセットは厳密に同じ指標ではない。
OSをまたぐ比較は同一環境のベースライン比較とみなさない。
Windows側でのコンパイル・実行完走はまだ実機確認していない。

計測対象は **jwcが生成した実行ファイル、rustcが生成した実行ファイル、clang++が生成した実行ファイル、go buildが生成した実行ファイルの4つだけ**。Rust製Jabberwockコンパイラはデフォルトではセルフホストjwcの初回ビルドのために使用するが、ベンチマーク結果に含めない。`--no-elide`、`--unchecked` は含めない。

同一ケースの測定は4者の実行順をラウンドごとに入れ替え、既定の8反復では先頭を担当する回数が各言語2回ずつとなる。任意の`--runs`で4の倍数以外を指定した場合は完全均衡ではない旨をJSONに記録する。すべての反復の標準出力が同一であることを要求する。**1回でも出力が変動するか、空の出力、非有限値・ゼロ時間など無効な測定値があればFAIL**。ただし順序の交互化でCPU負荷や周波数変動が完全に消えるわけではない。

出力は `target/benchmark-report.json`。各ケースについて4者すべての標準出力SHA-256が一致した場合にのみPASSとし、実行時間の中央値、最大RSS、jwc対Rust・C++・Goの比率を記録する。正の速度低下率は `(jwcの中央値 / 比較対象の中央値 - 1) × 100%`。機械環境、ビルドフラグ、ソース入力のSHA-256、生成に用いたjwcのSHA-256も保存する。

**旧計測の注意:** 以下に残す2026-10-25のベンチマーク表と従来の`bench/run.sh`はRust製Jabberwockコンパイラ・Go等を含む**旧方式**であり、セルフホストjwcの実測結果ではない。現在のjwc性能の主比較へ流用しない。

Linuxの計測は`wait4`、Windowsの計測はWindowsプロセスAPIを利用する。依存はPython 3、cargo/rustc（構築済みjwcを使う場合cargo不要）、clang/clang++、Go、Linuxではさらにlld、cc。コンパイラの最適化器やアルゴリズムの差は残るので、数値は個々のケースの比較であり言語全体の優劣を証明しない。

## 旧スイート・履歴資料

従来の`bench/run.sh`はGo、複数のJabberwock検査設定などを含む。互換・履歴用として残し、新しい`scripts/benchmark_report.py`からは呼び出さない。

解析の変更前後だけを比べる実験は `experiments/` に置く。`experiments/scalar-call.jw` は数値の補助関数の呼び出し後に残る要素 ref の検査を測るもの。

- Go と C++ は、それぞれの普通の書き方（Go の `map`・`slices.Sort`・バッファつきチャンネル、C++ の `unique_ptr`・`std::sort`・`unordered_map`）。
  C++ のチャンネルは jabberwock と同じ「上限なし」を錠と条件変数で書いたもの（Go だけバッファつきで、条件はそろっていない）。
  C++ の `vector<bool>` はビットで詰めるので、sieve は C++ に有利（メモリも 1/8）。
- jabberwock は 3 通りで作る（`jabberwock build` の測定用の切り替え。`jabberwock build --help`）:
  - **jabberwock**: ふつう（解析で消せる世代の検査を消す）。
  - **検査を全部残す**: `--no-elide`（解析をしない）。解析が取り戻した分が分かる。
  - **検査を全部消す**: `--unchecked`（世代の検査も添字の範囲の検査もしない。**安全でない**。検査の費用の上限を見るだけ）。
- 検査の数: 「場所」は書き出した検査の数（`--stats`）、「実行時」は実際に通った回数（`--count-checks` で作った別の実行ファイル。数えるぶん遅いので時間は見ない）。
  世代の検査は ref をたどるときと、読むだけの写し（for の要素など）の own をたどるときにある。本物の own をたどるときは検査がいらない。

### 読み方

- **ぶれ**: 同じ実行ファイルでも最小と最大で 10〜20% 動く（クラウドのコンテナで、周波数もほかの負荷も止められない）。10% 以内の差は誤差と見る。
  比べるのは同じ回の中だけにする（前の回とは環境が違う）。
- **Go と比べて**: 21 本のうち 15 本で jabberwock が速い（うち graph・mandelbrot・spectralnorm は 10% 以内）。fannkuch は同じくらい。
  負けているのは bst・chan・pingpong（スレッドの待ち合わせ）・refmut・linkedlist（2 割）。pingpong は 1 往復ごとに相手を起こすので、OS のスレッドを使う jabberwock・C++・Rust はどれも 2 秒（1 往復 40 マイクロ秒）、
  同じ OS のスレッドの上で goroutine を切り替える Go だけ 0.024 秒。jabberwock のチャンネルが遅いのではなく、スレッドの作りの違い。
- **C++・Rust と比べて**: 同じ LLVM なので、計算だけのもの（fib・mandelbrot・fannkuch・matmul・spectralnorm・parsum）はほぼ同じ。
  jabberwock が速いのは確保と解放が多いもの（shortlived は C++ の 0.43 倍、binarytrees は 0.57 倍。解放した区画を空きの鎖ですぐ使い回すため）。
  遅いのは refmut（下）・graph（添字の検査）・concat と sieve（C++ は文字列の作り方とビット詰め、下の「速くした書き方」）。
  sort と sortworst は Rust と同じくらいで、Go・C++ より速い（下の「並べ替え」）。Rust は bst・nbody でも一番速い。
- **世代の検査の費用**: 解析が効くのは particles（全部残すと 0.13 → 0.18 秒）と nbody（0.36 → 0.44 秒）。
  linkedlist はデータがキャッシュに収まるので、検査の費用が見える（5 億回通って 0.19 秒、全部消すと 0.16 秒。約 2 割）。bst・binarytrees はキャッシュミスに隠れる。
- **refmut（要素を借りた ref）**: `let p = ref mut ps[i];` で書くと、particles と同じ計算なのに 0.28 秒（particles は 0.13 秒）。
  前は世代の検査が 9.7 億回残っていたが、解析が「リストの要素を指す ref は、要素が動く操作までは生きている」と分かるようにして 0 にした
  （0.30 → 0.28 秒）。残りの差は、借りるときにリストの頭へ付ける印の書き込みと、ref と ps が同じ所を指しうるために読み直しが要ること。
  nbody も残っていた 150 回の検査がなくなった。
- **並べ替え（2026-10-25 に手順を変えて sort・sortworst・refmut・nbody を測り直した）**: 前のマージソートは sort 0.42 秒・sortworst 0.82 秒。
  整数の `sort()` は比べる関数を呼ばない基数ソートにして 0.15 秒・0.16 秒（Rust 0.14・0.16 秒、Go 0.66・1.05 秒）。
  `sort_by` は比べる関数を呼ぶ回数で決まるので、比べる回数の少ない手順（並んだ部分を使う Timsort の仲間）にした（300 万個のばらばらで 0.43 → 0.36 秒、
  並んだものは数ミリ秒）。安定でない `sort_unstable` / `sort_unstable_by` も足した（pdqsort。作業用の領域がいらない）。
- **添字の範囲の検査の費用**: graph で 0.38 → 0.24 秒（約 35%。添字でたどるので一番効く）、fannkuch で 0.24 → 0.20 秒、matmul は誤差の範囲。
  境界チェックつきの C++ も graph で 0.22 → 0.34 秒と、同じくらい遅くなる。ほかは C++ でも誤差の範囲。
- **短い命の値（shortlived）**: 1 億回の確保と解放で jabberwock が一番速く、最大メモリも 1.9 MB。同じ 16 個の区画を使い回すので、
  区画ごとの世代は解放と使い直しで 2 ずつ進み、終わりで約 1250 万（64 ビットの上限の約 7000 億分の 1）。
- **最大メモリ**: binarytrees・shortlived・words は Go・C++ より小さい。sieve は C++ の `vector<bool>` がビットで詰めるので C++ が小さい。
  sort は作業用の領域（n 個ぶん）のぶん C++・Rust より大きい。chan は上限なしのチャンネルで、送る側が先に進むぶん大きい（Go はバッファつき）。
- **並列（parsum）**: 4 スレッドで 1 スレッドの jabberwock 3.7 倍・Go 3.9 倍・C++ 3.2 倍・Rust 2.9 倍（4 コア）。Go は 1 スレッドの割り算が遅い。
- **ビルド時間と大きさ**: jabberwock は 1 本 0.6〜0.8 秒（実行時ライブラリも一緒に -O2 と LTO でつなぐ）で、Go・Rust・C++ より遅い。
  実行ファイルは 6〜25 KB で C++（libstdc++ をつなぐ）と同じくらい。Go は 2.1 MB、Rust は 4.2 MB（strip して 340 KB）。
- **起動の時間**: 何もしないプログラムは 4 つとも 2〜2.7 ミリ秒（ほとんどが fork と exec）。jabberwock の実行時ライブラリの準備の費用は見えない。
- **速くした書き方**: Go は sieve（最初に大きさを決める）で jabberwock より少し速くなり、concat と words も 4 割ほど縮むが、まだ jabberwock より遅い。
  C++ は concat（`to_chars` で直接足す）が 0.05 秒、sieve（大きさを決める）が 0.09 秒、words が 0.27 秒で、jabberwock より速い。jabberwock 側は素朴な書き方のまま。

### 同じアルゴリズムか（データ構造の違い）

| 名前 | jabberwock | Go | C++ | Rust |
|---|---|---|---|---|
| bst・binarytrees・linkedlist・shortlived | own（区画と空きの鎖） | GC | `unique_ptr`（malloc） | `Box`（malloc） |
| sort・sortworst | 整数なので基数ソート（並んでいればそのまま。結果は安定な並べ替えと同じ） | `slices.Sort`（pdqsort） | `std::sort`（introsort） | `sort`（driftsort。安定、並んだ部分を使う） |
| sieve | `bool[]`（1 バイト） | `[]bool`（1 バイト） | `vector<bool>`（**1 ビット**） | `Vec<bool>`（1 バイト） |
| words | 辞書（入れた順を覚える） | `map` | `unordered_map` | `HashMap`（SipHash。遅いが攻撃に強い） |
| concat | `s += "..."`（その場で足す） | `strings.Builder` と `Fprintf` | `+` で一時的な文字列 | `write!` |
| chan | 上限なし（錠 1 つ） | **バッファ 1024** | 上限なし（mutex と deque） | 上限なし（`mpsc::channel`） |
| pingpong | 上限なし | バッファなし | 上限なし | 上限なし（毎回待つので、どれも同じ動き） |
| chan・pingpong・parsum のスレッド | OS のスレッド | **goroutine** | OS のスレッド | OS のスレッド |

ほかのもの（fib・matmul・spectralnorm・nbody・particles・refmut・fannkuch・mandelbrot・graph・parsum）は、どの言語も同じ計算を同じ順でしている（小数の結果も一致する）。

### 回帰の見張り（CI）

`bench/checks.sh` が、各ベンチマークの検査の数（書き出した場所と、実行時に通った回数）を `bench/checks.txt` と比べ、
世代か添字の検査が増えたら（解析で消した数が減ったら）失敗にする。時間は共有のマシンでぶれるので見ない。
`.github/workflows/bench-checks.yml` で main への push ごとに走る。減ったとき・ベンチマークを足したときは `UPDATE=1 bench/checks.sh` で書き直す。
