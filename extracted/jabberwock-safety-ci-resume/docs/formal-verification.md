# 形式証明専用の検証様式

2026-10-26。実用テスト1〜12とは別に、形式証明をF1〜F5で管理する。
実用テストは具体的な入力・環境での動作を確認し、形式証明は明示したモデル・前提の下で命題を機械検査する。
両方を [検証体系](verification-plan.md) の同じ5目標へ対応づけるが、結果を合算して「全項目合格」にしない。

## 分類と現在の到達点

| ID | 対象 | 現在の形式証明 |
|---|---|---|
| F1 | コンパイルの意味保存 | 全変換の意味保存は未証明。実行器間の比較成功を証明済みに置き換えない |
| F2 | メモリ安全性 | [F2-001](../formal/records/F2-001-generation.md): 世代上限・退役・参照非復活の部分モデル。実際のheap/アドレス/アクセス全体との接続は未証明 |
| F3 | 型安全性 | 言語全体の型規則・評価状態と、その保存・進行の機械化は未完 |
| F4 | 所有権・参照の整合性 | [F4-001](../formal/records/F4-001-ownership.md): 抽象的な所有位置間のムーブ。参照の部分証明はF2-001も参照。複合値・回収・並行状態は未証明 |
| F5 | 実行時チェックと検査省略 | F2-001の抽象的な読書き判定のみ部分証明。実装の検査と省略の健全性は未証明 |

F1〜F5は分類であり、5つの定理だけで完了するという意味ではない。
証明する命題・関連する小さな定理群ごとに `F2-001` のようなIDを付ける。
複数領域に関係する定理は一つの記録を参照し、同じ定理を重複して成功数へ足さない。
既存のS/M/T/O/Cは詳細課題、ライブラリのL1〜L5は実用試験の分類として維持する。

## 一件の記録に必要な内容

[テンプレート](../formal/records/TEMPLATE.md) を複製し、次の内容を記録する。

| 欄 | 記録する内容 |
|---|---|
| 識別と目的 | 証明ID、関係するF/G/詳細課題、対応する仕様の版・節 |
| 命題 | 自然言語の主張、Leanの完全修飾定理名、型/命題の所在。量化する対象、前提、結論を分ける |
| モデルと範囲 | 状態・操作・観測結果、含める機能、除外する機能、有限/無限実行、失敗や非終了の扱い |
| 前提の妥当性 | 前提を満たす例、到達状態との関係、主張したい結論を前提へ置いていないことの確認 |
| 依存と信頼 | 実際の公理依存、Lean/標準ライブラリ/検査scriptの版。OSやC/LLVM等に関する仮定は独立して記載 |
| 証明の状態 | 下記の状態を記入。モデル内の証明と実装との対応を分ける |
| 実装との対応 | 対象commit/ソース、モデルと実装状態の対応関係、変換や操作ごとの対応定理、残る未証明経路 |
| 実行証拠 | 検査日時、モデル/検査器のcommit・ハッシュ、コマンド、終了コード、公理監査、ログ/Actions run/job、ローカルかCIか |
| 維持条件 | 再検査が必要な変更、反例や失敗、次に埋める課題、レビューで未確認の点 |

Leanが受理したことと、その命題が目的の言語仕様を表していることは別に確認する。
結論を仮定した命題、到達できない状態だけのモデル、対象操作を取り除いたモデルで、広い保証を主張しない。
モデルの反例は実装への攻撃成功とは区別する。有限個の例の評価も、一般化した定理の証明へ読み替えない。

## 状態と判定

証明の状態は以下から選ぶ。

- **未形式化**: 主張やモデルがLean等に定義されていない。
- **命題定義済み・未証明**: 命題はあるが、機械検査できる完成した証明がない。
- **モデル内証明済み**: 記録したモデル・前提の下で証明が通る。実装への保証はまだ主張しない。
- **実装接続済み（対象範囲限定）**: 記録した具体実装とモデルの対応も機械検査できる。対象外や信頼する外部部分を明示する。

機械検査の結果はこれと別に **成功 / 失敗 / 未実行 / 環境不備** を記録する。
証明ソースの状態だけを見て、今回の実行が成功したことにはしない。
形式化・モデル内証明・実装接続の進捗を、F分類全体や実用テストの合格数へ置き換えない。

「モデル内証明済み」と記録するには、対象命題のビルドと公理監査が成功し、証拠が同じモデルの版を指している必要がある。
「実装接続済み」とするには、単なるソースへのリンクや差分テストでは足りず、具体状態から抽象状態への対応と操作/変換の保存の定理が必要。
仕様やモデルの適切さについて未確認の点があれば、その範囲を明記する。

## 機械検査と記録の更新

既存の専用コマンドを使う。

```sh
python3 scripts/check_formal.py
```

専用CIは [formal-spec.yml](../.github/workflows/formal-spec.yml)。実用テストの `test` / `safety` とは別の結果とする。
Lean 4.24.0を固定し、全theoremの公理依存を確認する。
現在許す標準公理は `propext`・`Quot.sound`・`Classical.choice` のみ。証明の穴・独自公理・native実行への置換は拒否する。
版違い、Lean不足、証明失敗、監査漏れは成功にしない。CIジョブが開始されていない場合も未実行として扱う。

現行scriptはLeanのビルドと公理依存を検査する。**記録の全必須欄や、自然言語の主張と命題の一致を自動判定する機能はまだない。**
Markdown記録とJSONの実行証拠は確認した時点の記録であり、CI成功によって自動更新されるものではない。
記録を更新する際は実際の検査出力から定理名・依存・結果を転記し、未実行の欄を成功で埋めない。

仕様、定義、命題、証明、依存ライブラリ、検査器が変わったら、関係する記録を再検査・再確認する。
実装が変わったら、既存の実装接続の主張も再確認する。過去の成功記録は履歴として残し、最新実装の成功へ流用しない。
実装接続がない段階では、実装変更だけでモデルの定理が偽になるわけではないが、実装について言える範囲は広がらない。
