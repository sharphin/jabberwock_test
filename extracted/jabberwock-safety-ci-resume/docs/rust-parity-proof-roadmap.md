# Jabberwock: 安全性の形式保証とRust級の実用性へのロードマップ

作成: 2026-10-26。対象: Jabberwockコンパイラ、セルフホストコンパイラ、C runtime、言語仕様。
この文書は**計画**であり、未実施のテスト・未完成の証明を完了と表示しない。

関連文書: [実用検証の12項目](verification-plan.md)、[形式証明のF1〜F5と記録様式](formal-verification.md)、[安全性の現状](safety-testing.md)、[ローカル実行器](local-safety.md)。

## 0. 何を「超える」とするか

目標は「Rustのコンパイラ全体が形式的に未証明だから勝ち」という比較ではない。
Rustは実用上の型・所有権・メモリ安全性に強い実績を持つ。比較では**同じ仕様範囲、同じ条件、同じ故障モデル**を用いる。

評価を3本立てで分離する。

1. **安全性（必須）:** Jabberwockの定義したG1〜G5が、指定した言語仕様と実行構成で成り立つ。検証の対象・前提・信頼境界を明記する。
2. **性能（比較）:** 同じタスク・入力・最適化条件・マシンで、Rust実装とのレイテンシ、スループット、メモリ使用量、割当て数、コンパイル時間を計測する。「Rustより速い」は総合印象でなく事前定義した対象で判定する。
3. **学習・表現力（比較）:** 典型的な借用・グラフ・循環・可変コンテナ・並行処理課題で、正しく書ける割合、実装行数、エラー修正回数、所要時間、理解度を同条件で比較する。主観だけで「簡単」と判定しない。

一部の課題で優位でも「全ての点でRustを超えた」とは主張しない。

## 1. 安全性の判定を固定する

### 1-A 実用的な合格: 12項目

[verification-plan.md](verification-plan.md) に定義済みの12受け入れ条件を**全件**満たす。
`cargo test`の終了コード0、`PROBES_PASS_ONLY`、形式モデルの定理数を12項目の合格へ読み替えない。

現在の記録にある問題:
- **8:** インタプリタとRust/jwcネイティブで資源枯渇時の診断・終了状態が違う。
- **9:** ジェネリック型の具体化後に1 MiB配列上限を超える経路がある。
- **10:** Debug CLIのAST→IR比較により外部副作用が二重実行される。
- **11:** 途中評価・確保失敗・制御フロー・送受信・回収のケース台帳と注入試験が未完。
- **12:** Rustコンパイラ自体のDebug/Release、Linux/Windows、Rust/jwc、-O1/-O2+LTO、ABI、計装の負例とLSanについて未実行構成が残る。

1〜7の既存合格は、記録されたcommitと実行環境・ケースに限定して維持する。新しいコミットの合格とはしない。

### 1-B 「安全」の定義: G1〜G5の成立

| 目標 | 必要な命題 | 主要な実証 |
|---|---|---|
| G1 意味保存 | ソース意味論と各変換後の観測結果（値、規定エラー、I/O回数・順序、停止性の扱い）が対応 | 独立した仕様オラクル、実行器差分、IR/LLVM変換証明 |
| G2 メモリ安全性 | 全到達状態で、許可されない読書き・UAF・境界外・未初期化使用・競合が起こらない | メモリモデル、実際のruntime契約、sanitizer/負例 |
| G3 型安全性 | 型が保存され、値・次の遷移・規定エラー以外の行き詰まりに至らない | 型規則、preservation/progress、実コンパイラの型検査対応 |
| G4 所有権・参照整合性 | 全遷移で所有責任と参照有効性・必要な回収が保存される | move/borrow/drop/送受信・途中失敗のモデルと実装対応 |
| G5 チェック・省略の健全性 | 必要なチェックがpayloadへのアクセス前に働き、省略しても観測・安全性が保存される | 静的解析のsoundnessと生成LLVMへの対応 |

**形式モデルの証明**と**実装がモデルの操作を正しく実現する証明**を必ず分ける。
五つのG全体の達成を単なるテスト件数やLeanの22定理で宣言しない。

## 2. 形式証明の進め方（F1〜F5）

既存の `formal/` と [formal-verification.md](formal-verification.md) を拡張し、証明を作り直さない。

### 第I段階: 仕様・意味論を固定
- 言語の値、heap、世代、参照、所有権、型、エラー、スレッドの状態を機械可読に定義する。
- OOM、stack/thread失敗、非終了、I/O、`exit`、panic相当、FFIをモデルの対象か明示的な除外・前提に分類する。
- 検査省略あり・なし、Debug/Release、Rust/jwcで同じ観測規約を採用する。
- 最初は小さな核（整数、構造体、own/ref、分岐、関数、heap操作）に対象を絞り、対象外機能を明記する。

**出口:** バージョン管理された仕様、対象機能表、仕様由来の期待値、信頼境界一覧が揃う。

### 第II段階: 抽象機械の安全性
- **F3:** 型安全性のprogress/preservation。規定エラーはprogressの許容結果として厳密に定義。
- **F4:** 所有責任の一意性と保存、move/borrow/drop、例外的終了・評価途中・送受信を漸進的に追加。
- **F2:** heapアクセスの権限・有効性・世代退役・境界・整数オーバーフロー・確保失敗の安全な遷移を証明。
- **F5:** `check_ref`のsoundnessと、静的省略判定のsoundness（省略前後の双模倣または適切なrefinement）を証明。
- 状態の対応・不変条件が現実の実装に適用可能か、非自明な反例や負例で監査する。

**出口:** 各定理に完全修飾名、対象仕様の版、前提、公理監査、未証明経路を記録。

### 第III段階: コンパイラの意味保存（F1）
- AST→型付きAST→Jabberwock IR→LLVM IRの各段階に、ソースとターゲットの状態対応関係と観測保存を定義。
- 両方向の一致が不適切な最適化は、許される観測のrefinementとして定義し、未定義動作を勝手に仮定しない。
- 関数呼出し、整数幅、文字列、ジェネリック具体化、評価順、副作用、error path、threadを追加していく。
- Rustブートストラップ版とjwc版は、同じ正しさを単に相互比較するのではなく、双方が仕様に対応する証拠を取る。
- LLVM/clang全体の証明がない場合は、その意味論や生成コードに対する検証のどこまでを信頼するか明記する。

**出口:** 対象部分集合について、各変換の機械検査済み定理と実際に出力されたIRへの接続がある。

### 第IV段階: 実装への接続
- `src/`、`jwc/`、`runtime/jw_rt.c`の実装操作ごとに抽象状態との対応を確立。
- 実装の検証には、対象コードの検証・生成・再構築を伴う仕組みを用い、**Leanで書いた別モデルだけの証明をソース実装の証明と呼ばない**。
- 特にC側のポインタ計算、allocation/free、世代metadata、atomics、エラー時の再入/後処理を検証する。
- Cランタイムの全廃は必須ではない。信頼境界を縮める目的で、上位機能をJabberwockで実装し直す場合は旧実装との契約・振る舞いを移行ごとに比較し直す。
- OS、libc、LLVM、clang、リンカ、CPUのうち未証明のものを信頼計算基盤（TCB）として明示する。

**出口:** 主張する機能・構成に、証明されないギャップを残さない。または残るギャップを前提として限定した保証を明記する。

## 3. 開発順序（安全性が先、速度と使いやすさは並行計測）

| マイルストーン | 作業 | 完了判定 |
|---|---|---|
| M0 ベースライン | commit/ツールチェーン/OSを固定し12項目、性能・学習課題の初期値を記録 | 失敗・未実行・不明が分離された再現可能な記録 |
| M1 既知の欠陥 | 8: OOM契約と注入、9: 具体化後の型サイズ、10: 副作用1回を修正 | 専用回帰テストで失敗再現→修正→合格 |
| M2 実用安全性 | 11の全経路、12の全構成・検出器負例、1〜7の回帰検証 | **12項目全合格**、同一commit・定義済み環境での証拠 |
| M3 形式モデル | F2/F4/F5の既存証明を拡充しF3を導入、仕様を固定 | 機械検査、公理監査、仕様・モデルの対応 |
| M4 コンパイラ意味保存 | F1と最適化の証明、Rust/jwc双方の生成物へ接続 | 対象機能の変換に未証明経路がない |
| M5 ランタイム保証 | Cランタイムの検証・小型化または安全な層への段階移行 | heap/atomics/失敗経路の実装との対応 |
| M6 拡張と比較 | 仕様の対象全体を覆い、Rustとの性能・学習コストを比較 | 対象・前提を限定した再現可能な優位性の主張 |

M0→M1→M2を優先する。M3以降のモデル設計は並行可能だが、**試験合格は証明の代用ではない**。
機能追加で保証対象が増えたら、対象表・証明義務・回帰テストを更新する。

## 4. Rustとの比較でフェアにすること

性能:
- Rust/Jabberwockで同じアルゴリズム、データ構造、入出力とエラー契約を実装。
- 同一CPU・OS・コンパイラバージョン・最適化・温度/負荷条件で、複数回測定。中央値と分布を記録。
- 世代付きrefのチェック実行回数・省略回数を可視化し、速い/遅いケースをともに公開。
- 「速度がRustと同等」「特定分野で速い」「総合的に速い」は別の命題として扱う。

使いやすさ:
- Rust経験・習熟度が異なる被験者を偏りなく割当て、同じ課題と時間で比較する。
- コンパイル成功だけでなく、期待したエラー処理・所有権安全性・修正のしやすさも測定する。
- 一部の使い方が短く書けるだけで学習コスト全体の優位を主張しない。

安全性:
- RustはG1〜G5すべてを全実装について形式証明済みではないが、実用メモリ安全性の実績がある。
- 両言語に同じ「形式保証完了」の基準と明示した信頼境界を適用し、異なる基準の「合格」を並べない。
- 新しいJabberwockの証明が、Rustの安全性を一般に否定するものではない。

## 5. 判定の厳格なルール

- `IMPLEMENTED`（実装済み）、`TESTED`（指定範囲でテスト済み）、`MODEL_PROVED`（抽象モデルで証明）、`IMPLEMENTATION_LINKED`（実装への対応証明）、`G_GOAL_MET`（限定範囲のG目標達成）を区別する。
- `G_GOAL_MET` は仕様バージョン、対象機能、実行構成、TCB、証明IDと再検査ログが結び付いて初めて記録する。
- 未実行・skip・必要ツール欠如・サニタイザ負例の未検出は合格にしない。
- 形式証明は任意の未定義動作や「実装が正しい」という仮定で成立させない。Leanが受理した命題が意図した仕様を表すかレビューする。
- 証明した部分集合から言語全体への無条件な一般化を禁止する。
- G1〜G5達成は、この文書の定義する範囲での安全性であり、ユーザーの業務ロジック、外部サービスの安全性、OS自体の正しさを含めない。
