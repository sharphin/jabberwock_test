# スレッドの設計（案 A に決定。2026-10-23）

結論: **案 A「Go 風。`spawn` と `chan`。スレッドには own とコピーできる値だけを渡し、ref は渡せない」** から始めるのを勧める。
データの取り合い（data race）は、型検査だけで起きなくなる。ロックもライフタイムも書かなくてよい。

## 見た目（案 A）

```
fn i64 sum(own i64[] xs) {
    let mut s = 0;
    for x in xs { s += x; }
    s
}

fn main() {
    let a = own [1, 2, 3];
    let b = own [4, 5, 6];
    let t1 = spawn(() -> sum(a));     // a はスレッドへムーブ（もう使えない）
    let t2 = spawn(() -> sum(b));
    print(t1.join() + t2.join());     // 21。join で終わるのを待って、戻り値を受け取る

    let chan<str> c = chan();         // チャンネル。コピーしても同じチャンネルを指す
    let w = spawn(() -> {
        for i in range(3) { c.send("msg {i}"); }
        c.close();
    });
    loop {
        match c.recv() {              // Option<str>。閉じて空なら None
            case Some(m) -> print(m);
            case None -> break;
        }
    }
    w.join();
}
```

## 決まり（案 A）

| 項目 | 決まり |
|---|---|
| `spawn(f)` | 引数のない関数の値を新しいスレッドで動かし、`task<R>` を返す（R は f の戻り値の型） |
| `t.join()` | 終わるのを待ち、戻り値を受け取る。`task` はムーブする値（join は 1 回だけ。2 回目は実行時エラー）。join しないまま捨てると、捨てたところで待つ |
| 渡せる値 | f が取り込む値は「送れる型」だけ: 数・真偽・小数・文字列・own・構造体・enum・配列・リスト・辞書・`chan`（中に ref や関数の値を含まないもの）。**ref はエラー**（型検査で弾く） |
| `chan()` | 型は入れる先から決める（`let chan<T> c = chan();`）。T は送れる型。`send(v)` は v をムーブして渡す。`recv()` は `Option<T>`（閉じて空なら None）。`close()`。チャンネル自体はコピーできる（同じチャンネルを共有） |
| 送る大きさ | 今は上限なし（send は待たない）。上限つきは、あとで足す |
| スレッドの中のエラー | プログラム全体をそのエラーで止める（Go の panic と同じ）。表示はいつもと同じ時系列 |
| 全員が待ちで止まった | 「すべてのスレッドが待ちのまま止まりました」のエラー（Go と同じ） |
| print | 1 回の print の行は混ざらない（行ごとにまとめて出す） |

### なぜ安全か

- スレッドに渡るのは own（唯一の所有者）かコピーなので、2 つのスレッドが同じ場所を指すことがない。
- ref は渡せないので、別のスレッドが解放した区画を読むことも、世代チェックを取り合うこともない。
- 文字列は数を数えて共有しているので、送るときに複製する（スレッドの中では今までどおり速い）。

## ほかの案

| 案 | 中身 | 良いところ | 困るところ |
|---|---|---|---|
| **A（推奨）** | 上のとおり。own をムーブして渡すだけ | 簡単。型検査だけで安全。今の作りをほぼ変えない | 大きなデータを複数のスレッドで「読むだけ」共有できない（ムーブか複製） |
| B | A ＋ `scope { ... }` の中だけ、外の値を `ref`（読むだけ）で渡せる（Rust の `thread::scope`） | 大きな配列を分けて並列に計算できる | scope の間、借りた先を書き換え・解放できない決まりを型検査に足す。世代の数え方をスレッドに対応させる必要がある |
| C | A ＋ ロックつきの共有（`shared<T>`・`lock`） | ほかの言語に慣れた人には分かりやすい | デッドロックが書ける。ロックの中で ref を外に出さない決まりなど、覚えることが増える |

B と C は、A のあとに足せる（A の決まりを壊さない）。

## 作り方（案 A）

1. 型検査: `spawn` / `task<R>` / `chan<T>` と「送れる型」の判定（`sendable`）。仕様（spec.md）に追記。
2. インタプリタ: スレッドごとに別の `Interp`（別のヒープ）を本物のスレッドで動かす。送る値はヒープから切り離した形に直して渡す。
3. IR と突き合わせ: テストは join と chan で結果の順番が決まるものだけにする。
4. 実行時ライブラリ: 区画の空きリスト・生きている数・深さをスレッドごとに（`_Thread_local`）。チャンネルは mutex と条件変数（Windows は Win32 の同等品）。出力はロックして行ごとに。
5. 速さ: 並列に計算するベンチマーク（Go と比べる）。

## 実装の状態（2026-10-23）

1〜4 は済み。全テストがインタプリタ・IR・実行ファイルで同じ結果になる。

| 測ったもの（4 コア） | jabberwock（実行ファイル） | Go |
|---|---|---|
| fib(32) を 4 回（1 スレッド） | 0.09 秒 | — |
| fib(32) を 4 スレッドで | 0.03 秒（約 3 倍速） | 0.022 秒 |
| チャンネルで 100 万個送る | 0.19 秒 | 0.08 秒 |

- チャンネルは Go より 2 倍ほど遅い。全体で 1 つの錠を使っているため（推測）。チャンネルごとの錠にするのは、あとで。

## 同期のコスト（2026-10-30 に jw_rt.c を読んで調べた。優先度は低い）

| 同期 | 中身 | コスト |
|---|---|---|
| チャンネル・spawn・join | 全体で 1 つの錠 `g_lock` と条件変数 `g_cv`。待っているスレッドがいれば、状態が変わるたびに全員を起こす（broadcast） | 遅いのはここだけ。別々のチャンネルでも錠を取り合う |
| 世代チェック | relaxed の atomic な読み書き（x86・ARM ではふつうの読み書きと同じ命令）。足し算は所有者だけがするので read-modify-write はない | ほぼない |
| 区画の割り当て | 空きリストはスレッドごと（`_Thread_local`）。退役のときだけ CAS | ほぼない |
| print | spawn したあとだけ錠を取る | 1 スレッドのときはない |
| chan の数（rc） | コピーするとき・捨てるときに atomic の足し算・引き算が 1 回 | 小さい |

測った数（4 コア、実行ファイル。数回だけの参考値）:

| 測ったもの | jabberwock | Rust（OS スレッド） | Go |
|---|---|---|---|
| チャンネルで 500 万個送る（bench/jabberwock/chan.jw） | 0.68 秒 | 0.41 秒 | 0.42 秒 |
| 5 万往復（pingpong.jw） | 2.0 秒 | 2.0 秒 | 0.03 秒 |
| parsum.jw（1 → 4 スレッド） | 0.64 → 0.17 秒 | — | 1.03 → 0.26 秒 |

- pingpong が遅いのは OS のスレッドを起こす費用（Rust も同じ）。Go はゴルーチンなので速い。jabberwock の錠のせいではない。
- 直すなら: 値の出し入れはチャンネルごとの錠で行い、待つときだけ全体の錠で `g_blocked` を数える（待っている人がいない send は全体の錠に触らない）。
  デッドロックの判定は「確かめる → `g_blocked` を足す」と「送る → 0 に戻す」が同じ錠の中で順に起きることに頼っているので、単に錠を分けると、デッドロックでないのにデッドロックと判定しうる。
