# 言語と速度の改善レビュー

調査日: 2026-10-25。対象: main の `bccbca7d284964a9d6805a60cafd5f2ef15fc278`。
仕様、実装、既存の測定結果を照合した提案であり、以下の機能や最適化を実装したものではない。

## 判断の前提

- 解放後の使用と範囲外アクセスの検出、ライフタイム注釈なし、前から順に行う型検査を維持する。
- interp・IR・ネイティブの出力、エラー文、エラー位置をそろえる。関数の呼び出し順や、エラーより前に行う副作用も保存する。
- 数値は [bench/README.md](../bench/README.md) の既存結果。今回の環境で速度を再測定した値ではない。表の測定対象と今回の main は異なるので、実装着手時には同じコミットで基準値を取り直す。
- 倍率は予測しない。改善幅は実装して測るまで不明。`--unchecked` は安全性を外した比較用であり、製品で使う解決策にはしない。
- `filter` / `map`、クロージャ引数の自動借用、`drain`、入れ子の match、`ok_or` は実装済み。再提案しない。

## 速度

### P1. 外へ逃げない ref の実体を小さくする

**説明:** 要素への ref が関数外へ出ず、要素が動かず、参照先の解放もない区間では、ネイティブの ref を住所だけにできないか調べる。

**効く理由:** `src/ir/llvm.rs` の `borrow_gen` は要素を借りるたびに世代を読み、借用済みの印を OR して書き戻す。`make_ref` は住所・区画・世代・借りた位置の4要素を作る。
`refmut` の既存結果は世代チェックを全て消しても 0.280 秒（比較用の全検査なしは 0.271 秒）で、Go 0.187 秒、Rust 0.121 秒との差が残る。
生成した未最適化 LLVM IR にもループ内の借用印の書き込みがある。ただし、最適化後に何が残るかは未確認なので、これが時間差の全原因とは断定しない。

**安全:** 検査を消せることと、借用印を消せることは別の証明。残った ref があとで世代を読む可能性、リストの再確保・解放、別名、コールバックまで調べる必要がある。
単に `RefElem` のチェックが消えたという理由では印を消さない。失敗しない区間の内部だけを対象にし、外へ渡す場合は従来表現に戻す。
`ref mut` は排他的借用を意味しないため、引数へ一律に LLVM の `noalias` を付けてはいけない。

**確かめ方:** `refmut` / `particles` / `nbody` の最適化後の IR・アセンブリとロード・ストア数を比較する。別名からの push、ref の返却・格納、クロージャへの取り込み、途中の drop を差分テストに追加する。

**重さ:** 大。区画を OS に返してよいかというランタイムの判断にも影響する。似た例はコンパイラの逃避解析・集約値の分解（SROA）。

### P2. 関数が何を変えるかを解析する

**説明:** 関数ごとに「要素を動かす」「所有値を解放する」「不明な関数を呼ぶ」などを要約し、影響のない呼び出しで解析情報を残す。

**効く理由:** `src/ir/analyze.rs` は通常呼び出し・関数値・interface 呼び出しで `kill_elems` を呼び、全 `RefElem` を捨てる。
読み取り専用の小さな補助関数を挟むだけでも、以降の検査が残る。まず名前の分かる関数の「全リストを動かさない」証明から始め、別名ごとの精密化は後にする。
`refmut` は既に検査ゼロなので、この項目単独でその速度差は埋まらない。

**安全:** 再帰は固定点で求め、不明な関数値・動的呼び出し・捕捉した ref mut・解放処理は安全側に扱う。引数の型が `ref` というだけでは、別経路の書き換えを否定できない。

**確かめ方:** 同じ計算を関数へ分けた版とインライン版で消えた検査数を比較する。再帰、引数どうしの別名、コールバック中の push、別リストに見える同一区画をテストする。

**重さ:** 中〜大。似た例は手続き間の副作用解析・Mod/Ref 解析。利用者に効果注釈を書かせる必要はない。

### P3. 範囲の証明による添字チェックの削減

**説明:** `for i in range(a.len())` のような単純なループを最初の対象にし、同じリストの長さが変わらないと証明したアクセスだけ検査を消す。

**効く理由:** `src/ir/llvm.rs` の `index` は原則として符号・上限を検査する。既存表の `graph` は通常 0.379 秒、全検査なし 0.240 秒で、境界検査の最適化を試す価値がある。
ただし全検査なしとの差は測定ばらつきや生成コードの違いも含み、回収できる時間の保証ではない。`graph` の `dist[u]` のようなデータ由来の添字まで、単純なループ解析で消せるわけではない。

**安全:** range の上限はループ開始時の値であり、途中の pop・drain や別名経由の変更で現在の長さと違い得る。整数の一周、負の刻み、continue も扱う。
エラーの起きる検査をループ前に移すと、それ以前の print が消えるなど挙動が変わる。最初は「必ず通る検査の削除」に限定する。

**確かめ方:** `graph` / `fannkuch` / `sieve` を使い、最適化後の分岐も数える。空リスト、負添字、長さ変更、整数上限、エラー前の出力を3実装で照合する。

**重さ:** 中〜大。似た例は範囲解析、帰納変数解析、Java JIT の境界チェック除去。

### P4. チャンネル間の競合と無関係な起床を減らす

**説明:** 全体の待ち状態管理と、各チャンネルのデータ操作を分ける。第一段階は待ち先ごとの通知の試作と計測にする。

**効く理由:** `runtime/jw_rt.c` の send / recv は共通の `g_lock` を取り、`changed` は共通の条件変数を broadcast する。独立したチャンネルも競合し、関係ない待機者まで起こし得る。
ただし `pingpong` は C++・Rust の OS スレッド版とほぼ同じ約2秒。Go の約0.024秒は goroutine のスケジューラも違うため、ロック分割だけでこの差が埋まるとは言えない。

**安全:** デッドロック検出を維持する。待機登録と状態変更の間の通知取りこぼし、close と send の競合、未受信の own の解放、終了した task の処理が難所。
バッファ上限を付けると send が待つという仕様変更になるので、既存の上限なしチャンネルの最適化とは分ける。

**確かめ方:** `chan` / `pingpong` に加え、独立した多数のチャンネル、複数送受信者、close 競合、join と recv が混ざるデッドロックを反復する。スループットだけでなく待ち時間・コンテキスト切替も測る。

**重さ:** 大。Go の軽量スレッドはさらに別の大規模案であり後回し。似た例は待ち先ごとの condition variable と parking。

### P5. 木の区画配置と列挙型の表現を測る

**説明:** まず Node と `Option<own Node>` の実際の大きさ・配置、キャッシュミスを測定し、型ごとの配置や列挙型の小型化を試す。

**効く理由:** `bst` は通常 3.851 秒、全検査なし 3.822 秒と近い。世代検査だけを狙うより配置を調べる根拠になるが、キャッシュミスが原因と確定したわけではない。
`block_alloc` は既にサイズ別の空きリストとスラブを使う。「プールを導入する」だけでは新しい改善にならない。`linkedlist` は逆に全検査なしで 0.192 → 0.156 秒なので、読み取り中に所有木が変わらない証明の対象にもなる。

**安全:** 木の親が生存していても、別の ref mut から子の own を drop できる可能性がある。親の生存だけでは子の ref の検査を消せない。
古い ref が読む世代領域を OS に返したり、区画の頭を無条件に削除したりしない。`Option<own T>` の空値表現を使うなら、読むだけの写しのタグや解放処理も整合させる。

**確かめ方:** `bst` / `linkedlist` と、既に速い `binarytrees` / `shortlived` を一緒に測る。RSS、キャッシュミス、確保回数も記録する。区画再利用後の古い ref と入れ子 own の解放を突き合わせる。

**重さ:** 大。似た例はサイズ別アロケータ、型別スラブ、Rust の Option の空値最適化。適用可能性は現表現の実測が必要。

## 言語と開発体験

### L1. checked 演算と失敗する数値変換

- **説明・効く理由:** `checked_add` / `checked_sub` / `checked_mul` を先にそろえる。サイズ計算、件数、ファイル形式の読み込みで、一周する通常演算を手で検査せずに済む。その後に範囲を検査する変換を検討する。
- **安全:** 通常演算と `as` の既存の意味を変えない。失敗を `Option<T>` で受けるなど、既存の型と `?` で表せる設計を選ぶ。名前と関数・メソッドのどちらにするかは未決定。
- **確かめ方:** 全整数幅、符号の境界、usize、成功・失敗、戻り値への `?` を interp・IR・ネイティブ・jwc で比較する。
- **重さ・似た例:** 中。Rust の checked 演算。小さな API でも全バックエンドと型検査への追加が必要。

### L2. 文字の処理をリスト化せずに行う

- **説明・効く理由:** まず `for c in s` のような逐次処理と、必要な文字判定 API を検討する。現状の `chars()` は `str[]` を返し、`jw_str_chars_list` はリストを構築する。大きな入力の字句解析では、中間リストを作らないことが文字型の追加より直接効く可能性がある。
- **安全:** 「文字」が Unicode scalar value か、見た目の文字のまとまりかを明記する。UTF-8 のバイト添字と既存の文字添字を混同しない。最初は既存の1文字 str を渡す形でもよく、文字型導入は別に判断する。
- **確かめ方:** 電卓・単語分割・ソース解析で時間と割り当てを測る。日本語、補助平面の文字、結合文字、空文字を検証する。
- **重さ・似た例:** 中。Rust の chars、Go の rune。文字型自体は型・文字リテラル・変換まで含めると大。

### L3. フォルダを分けたモジュールと公開範囲

- **説明・効く理由:** `use a.b;` と、フィールド・メソッド単位の公開範囲を優先する。自己ホストコンパイラやパッケージを育てるときに、ファイルの平坦化と実装詳細の公開を避けられる。
- **安全:** ライフタイム推論を増やさず実現できる。直接依存だけが使える規則とパッケージごとの名前空間を維持し、循環・同名・相対パスの扱いを決める。
- **確かめ方:** alice の複数パッケージで同名モジュール、private へのアクセス、循環、Windows のパスをテストする。
- **重さ・似た例:** 中〜大。Rust / Go のモジュールと公開範囲。まずフォルダ、次に細かな公開範囲と分割できる。

### L4. interface の型による分岐

- **説明・効く理由:** interface で受けた値の具体型を、失敗可能な操作で調べる。異種オブジェクトの処理に使えるが、種類が閉じている問題では既存の enum + match で足りるかを先に判断する。
- **安全:** まず読み取り用の ref を返す形を検討する。own を取り出す形は成功時だけムーブする規則が必要。失敗時に元の値を失わせない。無検査キャストを追加しない。
- **確かめ方:** 一致・不一致、ジェネリックな構造体、別モジュール、元の持ち主の drop、ref mut の扱いを突き合わせる。
- **重さ・似た例:** 大。Go の type switch / 型アサーション。実行時の型識別と所有権の扱いが難所。

### L5. 標準ライブラリを小さい実用例から育てる

- **説明・効く理由:** ファイル入力・文字列処理・Result の補助を小さなパッケージとして整理する。新構文より、設定ファイルや小さな CLI を最後まで書けることを優先する。
- **安全:** 既存機能で書ける範囲から始める。辞書の構造体キーは等値・ハッシュ・キー変更の規則が必要なため後回し。関数フィールドも取り込み・ムーブの規則を先に固める。
- **確かめ方:** 小さな CLI、設定読み込み、複数パッケージのアプリを作り、必要な操作と回避コードを記録する。
- **重さ・似た例:** 小〜中のパッケージへ分割可能。Go / Rust の標準ライブラリを参考にするが、巨大な一括導入はしない。

## 先に直したい文書と道具

- `spec.md` 11章の「f32・文字型・const はこれから」は、1章と parser の const 実装に反する。const を未実装扱いしない。
- spec 冒頭の対象日付は、後から追加された機能の状態を読み取れない。仕様の対象コミットか更新日の管理が必要。
- `src/project.rs` の `stale` はソースと manifest の更新時刻を見るが、コンパイラ・埋め込まれた runtime・オプションの変更を入力に含めない。古い実行ファイルで改善を測ってしまうのを防ぐため、ビルド指紋を保存する案がある。変更時だけ再ビルドするテストを付ける。規模は中。
- clang 不在時に `tests/native.rs` / `tests/fuzz.rs` / `tests/jwc.rs` は return する。Cargo の「成功件数」をネイティブの検証件数とみなさない。必須 CI では実際に clang が起動できることを前提として確認する。

## 優先順位

| 順位 | 対象 | 理由 |
|---|---|---|
| 1 | 文書の状態整理・ビルド指紋・測定の基準作成 | 誤った機能一覧や古い実行ファイルを根拠に判断しないため |
| 2 | L1 checked 演算 | 既存仕様を変えず、日常の安全なサイズ計算を改善できる |
| 3 | P1 の計測と小さな試作 | refmut は検査ゼロでも差が大きく、残る生成コードを調べる価値が高い |
| 4 | P2 関数の影響解析 | 検査削減と P1 の証明の両方に使える基盤になる |
| 5 | P3 単純ループの範囲証明 | graph などに差があるが、証明できる狭い形から進められる |
| 6 | L2 文字の逐次処理・L5 小さなライブラリ | 実用例を増やし、機能不足を具体的に確認できる |
| 7 | L3 モジュールと公開範囲 | 規模が大きくなったときの設計を助ける |
| 8 | P4 チャンネルの競合削減 | 効果は期待できるが、デッドロック検出と通知の正しさの負担が大きい |
| 9 | P5 区画配置・所有木の解析 | 既に速い確保処理の退行リスクがあり、プロファイルが先 |
| 10 | L4 interface の型分岐 | enum で代替できない実用例を確認してから所有権の規則を決める |
| 11 | f32・構造体キー・関数フィールド・軽量スレッド | 専用の需要か大きな設計が必要。現在の主要な差を直接埋める保証はない |

いずれも一つずつ PR に分ける。速度変更は基準コミットとの同条件の測定、機能変更は仕様・実装・3実装の差分テストを一緒にレビューする。

## 今回の確認範囲

- Rust 1.90.0 で `cargo build --release --locked -j 4` を実行し成功。
- refmut / graph を `--ll` で LLVM IR に書き出した。未最適化の出力では refmut に借用印の OR が1か所、境界エラーの呼び出しが2か所、graph に境界エラーの呼び出しが12か所ある。これは実行回数や最適化後の命令数ではない。
- clang 不在のため、ネイティブの性能比較、ネイティブとの突き合わせ、jwc の自己ホストは今回未検証。システムへの clang 導入は読み取り専用のパッケージ管理領域により実行できなかった。
- 元の測定の条件差（C++ の bool のビット詰め、Go のチャンネル容量・goroutine、最適化フラグ）も含めて比較する。特定の表だけから言語全体が速い・遅いとは結論しない。
