# コンパイラを jabberwock で書き直すために足りないもの

ゆくゆくはコンパイラ（今の Rust の実装）を jabberwock で書き直す（自己ホスト）。そのために今の言語で足りないものを、
小さなプログラムで 1 つずつ試して洗い出した（2026-10-24）。

## 試して、もうできると分かったこと

コンパイラの骨組み（字句解析 → 構文木 → 解析 → 書き出し）は、今の言語でも書ける。`examples/calc.jw` が小さな見本。

- 再帰する構文木: `enum Expr { Bin(str op, own Expr l, own Expr r); ... }`、`(own N)[]` を持つ構造体
- 借りた match で構文木をたどる（`match ref t { case N(l, r) -> sum(l) + sum(r); }`）
- 構造体のリスト・辞書の中をその場で書き換える（`v[i].a *= 10`、`m["x"].inc()`）
- 記号表から ref を返す（要素が `own S` なら `ref m[k]` で借りられる）
- interface のリスト `(own Sh)[]`、辞書 `get` / `contains`、文字列の比べ方・`chars()`・`"{n}"` で数を文字列に

構造体の値そのもの（own でないもの）はリスト・辞書の中から借りられないが、要素を `own` にすれば借りられるので、書き方で避けられる。

## 足りないもの

### A. ないと書けない

| # | 機能 | なぜ要るか | 案 |
|---|---|---|---|
| A1 | ファイルの読み書き（済み） | ソースを読む・`.ll` を書く | `read_file(path)` → `Result<str, str>`、`write_file(path, s)` → `Result<(), str>` |
| A2 | 外部コマンドの実行（済み） | clang を呼ぶ | `run_command(cmd, args)` → `Result<i64, str>`（終了コード） |
| A3 | 終了コード・標準エラー（済み） | エラーで止まる・エラーを表示する | `exit(n)`、`eprint(...)` |
| A4 | 文字の番号・バイト（済み） | 名前に使える文字かの判定、LLVM の文字列の `\HH`、ハッシュ | `s.bytes()` → `u8[]`、`c.code()`（1 文字目の番号）、`chr(n)` → `str`（この形で足した） |
| A5 | 文字列を後ろに足す速さ（済み。join は C6） | `.ll` は数 MB になる。今の `s += x` は毎回まるごと複製するので、2MB 作るのに interp で 34 秒、実行ファイルで 59 秒かかる（2 乗に遅くなる） | 持ち主が 1 人なら複製せずにその場で足す。あわせて `str[]` の `join(sep)` |

### B. ないとかなり面倒

| # | 機能 | なぜ要るか | 案 |
|---|---|---|---|
| B1 | ビット演算 `&` `\|` `^` `<<` `>>` `~`（済み） | ハッシュ、整数の幅の計算、印のビット | C と同じ記号と強さ |
| B2 | 16 進数の書き方 `0xff`、エスケープ `\r` `\0` `\u{...}`（済み） | 字句解析・書き出し | |
| B3 | 小数の読み取りとビット（済み） | 小数の書き方を読む・LLVM の小数の定数（16 進のビットで書く） | `s.to_float()` → `Option<f64>`、`x.to_bits()` → `u64` |
| B4 | `const`（済み） | 予約語の表・上限の数など | トップレベルの `const N = 5000;` |

### C. あると楽（なくても書ける）

| # | 機能 | 代わりの書き方 |
|---|---|---|
| C1 | フォルダを分けたモジュール `use ir.lower;` | 1 つのフォルダに `ir_lower.jw` のように並べる |
| C2 | 構文木に解析の結論を書き込む（Rust の `Cell`） | 式に番号をつけて、番号 → 結論の辞書に置く |
| C3 | 構造体のフィールドに関数の値 | enum と match で分ける |
| C4 | 実行時ライブラリ（C のソース）を中に入れる | `"""..."""` の文字列としてモジュールに置く |
| C5 | 値として使う match / if の中の `return`（済み）（`let n = match t { case Some(x) -> x; default -> return Err(...); };`） | いったん Option にして `ok_or(...)?`（examples/tinyc.jw の let のところ） |
| C6 | `str[]` の `join(sep)`（済み） | `s += x` をくり返す（その場で足すので速い） |

スレッド・interface の型での分岐・辞書のキーに構造体は、コンパイラには要らない。

## 進め方

A → B の順に足す。足したものは表の名前に「済み」をつける（A1〜A5・B1〜B4 は 2026-10-24。あわせて値なしの値 `()` も足した。A5 の結果は bench/README.md の concat）。どれも interp・IR・実行ファイルの 3 つで同じに動くようにし、テストで突き合わせる。
A5 は速さの問題なので、ベンチマーク（`bench/`）にも文字列をつなぐものを足した（concat）。

## 見本: examples/tinyc.jw

足した機能だけで書いた小さなコンパイラ。`let x = 式; print 式;` の言語を字句解析 → 構文木 → LLVM IR にして
`write_file` で書き、`run_command` で clang を呼んで実行ファイルにし、動かす。書いてみて見つかった不便が C5（もう直したので、let のところは match の中で return してもよい）。
（デバッグビルドの jabberwock は IR でももう一度動かして突き合わせるので、`run_command` の出力が 2 回出る。）

## 設計方針（案。2026-10-24）

jabberwock で書いたコンパイラ（以下 jwc）をどう作り、どう Windows で動かすか。

### 1. 出力はいまと同じ「LLVM のテキスト → clang」

- jwc も今の Rust 版と同じく `.ll` を書き、clang で実行ファイルにする。アセンブラやリンカーは自分で作らない。
- 書き出す `.ll` には OS の印（target triple）を入れていない。clang が自分の OS に合わせて決めるので、**同じ `.ll` が Windows でも Linux でも使える**。
- OS ごとに違うのは実行時ライブラリ `jw_rt.c` の `#ifdef _WIN32` の部分（端末の UTF-8・引数の UTF-16・錠・ファイル・コマンド）と、clang に渡すつなぐ指定（Windows は `-lshell32`、ほかは `-lm -pthread`）だけ。
- なので jwc そのものは OS を気にせず書ける。「Windows のコンパイラ」は、jwc のソースを Windows で `jabberwock build` したもの（`jwc.exe`）になる。

### 2. 作るのは「コンパイラに要る段」だけ

| 段 | 今の Rust 版 | jwc で |
|---|---|---|
| 字句・構文・モジュール | lexer / parser / modules（約 2,750 行） | 作る |
| 型検査 | types（約 2,900 行） | 作る |
| IR への書き出し | ir/lower（約 1,850 行） | 作る |
| LLVM の書き出し | ir/llvm（約 4,070 行） | 作る |
| 世代チェックを消す解析 | ir/analyze（約 420 行） | あとで（なくても正しく動く。速さだけ） |
| インタプリタ・IR の実行・AST の解析 | interp / ir/exec / analyze | 作らない（Rust 版に残して、正しさの基準にする） |

### 3. 正しさは Rust 版との突き合わせで確かめる

- 段ごとに、同じ入力で Rust 版と同じものが出るかを比べる（`--ir` の IR のテキスト、`--ll` の LLVM のテキスト）。今あるテストの jabberwock プログラムをそのまま入力に使える。
- 最後は自分で自分をコンパイルする: Rust 版で作った jwc（1 代目）が jwc をコンパイルして 2 代目を作り、2 代目が作った `.ll` が 1 代目のものと一字一句同じなら完成。
- Rust 版はそのあとも残す（インタプリタと、言語を変えるときの基準として）。

### 4. 順番

1. **Windows で今の Rust 版が本当に動くか確かめる。** `jw_rt.c` の Windows の部分は、Linux で文法を調べただけで、まだ一度も Windows で動かしていない。GitHub Actions の Windows で `JW_NATIVE=1 cargo test` を走らせるのが一番早い。
2. jwc を字句 → 構文 → 型検査 → lower → llvm の順に書き、段ごとに突き合わせる。
3. 自分で自分をコンパイルする。
4. Windows で jwc.exe を作って、同じ突き合わせをする。

## 進み具合

| 段 | jwc のファイル | 突き合わせ | 状態 |
|---|---|---|---|
| 字句解析 | `jwc/lexer.jw`・`jwc/diag.jw`（エラー表示） | `--tokens`（Rust 版の `token_dump`） | 済み（2026-10-24。リポジトリの .jw 全部とエラーの例で一致） |
| 構文解析 | `jwc/ast.jw`・`jwc/parser.jw`・`jwc/modules.jw`・`jwc/astdump.jw` | `--ast`（Rust 版の `ast_dump`） | 済み（2026-10-24。リポジトリの .jw 全部・テストの全プログラム 559 本・構文エラーとモジュールの例で一致） |
| 型検査 | `jwc/ty.jw`（型）・`jwc/typeck.jw` | `--typed`（Rust 版の `typed_dump`。式の型・変換の印・型の引数・変数と戻り値の型） | 済み（2026-10-24。リポジトリの .jw 全部・テストの全プログラム 568 本（型のエラー 279 本を含む）・モジュールの例で一致） |
| IR への書き出し | `jwc/ir.jw`（IR の形と表示）・`jwc/lower.jw` | `--ir-raw`（Rust 版の `ir_dump`。解析の前の IR） | 済み（2026-10-24。リポジトリの .jw 全部・テストの全プログラム 568 本・モジュールの例で一致） |
| IR の解析 | `jwc/analyze.jw` | `--ir`（`ir_dump` の解析のあと。消せた検査は `(*x)`、残した検査は `(*!x)`） | 済み（2026-10-24。同じ範囲で一致） |
| LLVM の書き出し | `jwc/llvm.jw`（型の形と手伝いの関数）・`jwc/llvmfn.jw`（関数の本体と `emit`） | `--ll`（Rust 版の `llvm_text`。書けないときの標準エラーも） | 済み（2026-10-24。リポジトリの .jw 全部・テストの全プログラム 568 本・モジュールの例で一致。jwc 自身を書き出したものも Rust 版と一字一句同じ） |

- jwc は ASCII でない文字をすべて名前に使える文字として扱う（Rust 版は Unicode の英字だけ）。正しいプログラムでは違いは出ない。
- 書いてみて見つかった不便:
  - 値として使うブロックの最後を `exit(1);` にできない（`;` を外して `exit(1)` と書く）。
  - 借りた match（`match ref`）では、中身が構造体・リスト・Option の値だと受け取れない。構文木の enum の中身はすべて `own X`（`own Expr[]` など）にした。
  - 変数に組み込みの関数と同じ名前（`args`・`print`・`exit` など）をつけられない。メソッドの中では、ローカル変数にフィールドと同じ名前をつけられない。
  - リストに `slice` / `contains` がない（小さな関数を自分で書いた）。
  - 文字列の埋め込み `{...}` の中に `"` を書けない（先に変数に入れる）。
  - 構造体のフィールドにあるリストを値として取り出せない（`drain()` で取り出すか、写す関数を書く）。型検査では見つからず、実行してから分かる。
  - IR に書き出せない: リストの要素の中のリストを `for (i, x) in a[j].xs` で回す（`for i in range(...)` で書き直した）。
    → 2026-10-24 に直した（添字はリストの写しから数える）。
  - 関数の結果（一時的な値）を `ref` の引数に渡せない（`ty.is(ty.inner(t), "Own")` が書けない）。型検査は数百か所あるので一番の手間だった。
    → 2026-10-24 に言語を変えて渡せるようにした（design-decisions.md「一時的な値を ref の引数に渡す」）。
  - 構造体のフィールドにある enum（`v.t` など）を値として読むと、実行してから「フィールドにある enum は取り出せません」になる（型検査では見つからない）。
  - `match` の値の中から `continue` / `break` できない（値を決めてから使う）。
  - フィールドの名前がモジュールと同じ（`d.ty.kind`）だとモジュールの名前と読まれていた。→ 2026-10-24 に直した（`.` のすぐあとの名前はモジュールとして読まない）。
  - `for x in a` の要素 x は写しなので、x を借りた ref をリストに残すと、次の周回で「無効になった参照」になる（実行時に見つかる）。
    要素の中の own の先（`match ref x.kind { case Lambda(l) -> ... }` の l）なら元の値を指すので残せる。
  - 構造体のフィールドにある辞書も値として取り出せない（写してから使う）。
  - `const` に `pub` をつけられず、モジュールの外から定数を使えない（値を返す `pub fn` を書いた）。
  - 文字列の中の `{` はいつも埋め込みなので、LLVM のテキスト（`{ ptr, i64 }`）は `{{` `}}` と書く。
- 速さ: jwc 自身（約 1 万 5 千行）の `--ll` は、-O2 の jwc で約 6 秒（Rust 版は約 2 秒）。
  IR の解析の事実を変数の数だけの表で持つと、写すのと消すのに時間がかかり -O0 で 82 秒だった。分かっている変数だけを並べる形にして 11 秒。
- -O0 で作った jwc は、jwc 自身を読むとスタックがあふれる（8 MB）。LLVM の書き出しが関数の中の一時的な値をすべて関数の入口の `alloca` に置くので、
  大きな関数の枠が大きく、`+` を長くつないだ定数（llvm.jw の PRELUDE）を再帰でたどると深くなる。-O1 以上なら枠がまとまってあふれない。

## 自分自身のコンパイル（2026-10-24）

`jwc build [--release] [-o 出力] [--clang clang] <file.jw>` で実行ファイルまで作れる（Rust 版の `jabberwock build` と同じ手順。-O2、LTO を試してだめなら LTO なし）。
実行時ライブラリは `jwc/runtime.jw` に文字列として入れてある（runtime/jw_rt.c から tests/jwc.rs の `runtime_is_up_to_date` が作る。ずれたらテストが失敗する）。
Rust 版と違う点: 途中のファイル（`出力.ll` と `出力.jw_rt.c`）は出力と同じフォルダに残る（ファイルを消す関数がまだない）。
別の clang は環境変数 `JW_CLANG` ではなく `--clang` で渡す（環境変数を読む関数がまだない）。Windows 用の `-lshell32` は付けない（llvm-mingw は最初からつなぐ）。

確かめたこと（Linux）:

1. Rust 版の `jabberwock build jwc/main.jw` で 1 代目の jwc を作る。
2. 1 代目の `jwc build jwc/main.jw` で 2 代目、2 代目で 3 代目を作る（1 回およそ 5 分。ほとんどは clang）。
3. 1 代目と 2 代目が書き出した jwc の `.ll` は同じで、Rust 版の `--ll` とも一字一句同じ。2 代目と 3 代目の実行ファイルはバイト単位で同じ。

これで、Rust がなくても（jwc の実行ファイルと clang があれば）jwc を作り直せる。テストは時間がかかるので 2〜3 の全体は入れず、
`jwc build` で例を実行ファイルにして interp と出力を比べるもの（`jwc_build_makes_an_executable`）と、jwc 自身の `--ll` の突き合わせを入れている。
