## 実用上の安全確認

オーナーの補足により、今回の判断基準は5目標すべての形式的な保証の完成ではなく、
現行コンパイラの改良やライブラリ実装を進めるための実用上の試験水準とする。
1〜9を基礎に、以下の3分類を追加して **コンパイラの項目1〜12** とする。
実行構成の確認も独立した12番として追跡する。

|---|---|---|

既存試験を廃棄したり全て作り直したりせず、各項目に対応するケースを再利用し、不足だけを追加する。

### 12項目と5領域の関係

| 領域 | 主な実用試験の項目 | この段階で判定すること |
|---|---|---|
| 意味保存 | 1・4・5・7・10・12 | 対象ケースの値・診断・評価順・外部効果が仕様の期待値に一致する |
| メモリ安全性 | 2・3・4・6・8・9・11・12 | 対象経路の不正アクセス、競合、未初期化、サイズ計算、失敗時の扱いを検出・拒否する |
| 型安全性 | 2・7・9・10・12 | 型の正常系を受け付け、不正な型・権限・変換を拒否し、具体化後の型と表現を照合する |
| 所有権・参照 | 2・3・7・8・11・12 | 参照の有効性と無効化、退役、責任の移動、仕様で必要な回収が対象経路で正しい |
| 実行時チェック | 1・2・4・5・6・7・10・11・12 | 対象アクセスの許可/拒否と、省略あり/なしの結果が一致する |

想定する到達点は、**5領域すべてについて、定めた機能・ケース・実行構成で実用上の試験基準を満たすこと**。
12個の見出しがあることだけで達成にはならない。対象ケースと必須構成を一覧にし、同じ実装に対する成功記録が必要になる。
この限定した判定には全23課題の形式証明を前提としない。一方、下記のG1〜G5全体を保証済みとする判定は、別の長期目標のまま維持する。

### 追加項目の判定上の注意

- 10では複数の実行器が同じ誤りを持つ場合も考え、実装の出力から転記していない期待値を用意する。
  比較する実行器ごとに外部効果の記録先を分離し、通常実行の副作用を比較のために二重に起こさない。
- 11では仕様が回収を要求する経路を列挙する。`exit`や既存の異常終了へ、仕様にない全面的な回収保証を追加しない。
  live payload、退役metadata、allocatorの保持量を区別し、保持メモリの上限や確保失敗の契約は8と対応づける。
- 12では`cargo test --release`の件数だけを根拠にしない。現在のAST→IR/native照合にはdebug専用の分岐があるため、
  releaseでも同じ比較が実際に動く入口を用意する。検査省略をdebug_assertだけで確かめた状態を、releaseの成功にしない。
  必須構成の未実行・skip・実行基盤の失敗は、その構成の合格に数えない。LSanの未実行も別に記録する。

2026-10-26、実装`36d4df2`のdebug CLIで、`run_command`から一時ファイルに1文字追記するプログラムを実行し、
終了0でも2文字追記されることを確認した。`src/lib.rs`の`run_inner`はAST実行後にIRでも実行するため、
外部効果も繰り返される。これは既存のCLAUDE.mdにも記録された動作であり、新たな退役処理が原因ではない。
項目10で解消・検証する対象として扱う。今回の文書更新では本体の修正や追加試験の実装は行っていない。

後続の [追加実行](practical-retest.md) では、release全体試験と外部効果の16ケースを実行した。
debugの副作用二重実行、8/9の不合格、11/12の未完了事項は引き続き残る。

## G1: 意味保存（S1〜S5）

観測するのは値、標準出力/標準エラー、診断の種別と対応するソース位置、外部効果の順序と回数、終了/非終了。
並行実行や資源制約では、仕様が許す差と比較方法を先に固定する。
任意の資源エラーを許して不正な変換を正当化しない。

| ID | 検証課題と合格条件 | 既存の入口と不足 |
|---|---|---|
| S1 | 字句・構文・糖衣構文。優先順位、結合、数値/文字列、Unicode、複合代入、評価回数を仕様の期待値と照合。不正入力は規定の段階で拒否 | [jwc](../tests/jwc.rs) のtokens/AST照合等が入口。Rust/jwcが同じ誤りを持つ場合の独立した仕様照合を拡充 |
| S2 | 名前解決・モジュール・型引数の展開。束縛/可視性/具体化した型が対応する実体を指し、再配置や順序で意味が変わらない | [modules](../tests/modules.rs)、[project](../tests/project.rs)、[generics](../tests/generics.rs)、[interfaces](../tests/interfaces.rs)。全変換の対応は未証明 |
| S3 | AST→IR。分岐、短絡、loop、break/continue、return、`?`、引数と一時値の評価順・回収・外部効果が一致 | [ir](../tests/ir.rs)、[control](../tests/control.rs)、[results](../tests/results.rs)、[system](../tests/system.rs)。仕様の評価状態とのシミュレーションと副作用一回の専用検証が必要 |

| ID | 検証課題と合格条件 | 既存の入口と不足 |

| O1 | 所有責任の保存。生成・ムーブ・引数・戻り値・一時値の各状態で所有者が重複せず、処理途中でも責任が消えない | [ムーブの部分モデル](../formal/JabberwockFormal/Ownership.lean)。一意性だけでなく、生きたpayloadと評価途中の全所有位置の対応が必要 |

| O4 | 無効化と維持。解放・変数ムーブ・リストの長さ/順序変更・送信では該当refを無効にし、通常のownムーブや要素代入等では有効性を保つ | [lists](../tests/lists.rs)、[borrow](../tests/borrow.rs)、既存1/2。pathと複合値、退役時の継続/停止まで接続する必要 |
| O5 | スレッド間の責任移動。送信・受信・join・taskの破棄・channel終了で、唯一の所有責任と古いrefの無効化を保つ | [threads](../tests/threads.rs)、送信後の再利用3経路。入れ子の所有グラフと並行モデルへの拡張が必要 |

正常終了時の残存区画0は重要な実行時の証拠だが、全途中状態での所有責任保存の証明ではない。
`exit`や既存の `_Exit` による異常終了は、現在の仕様にない全面的な解放保証を勝手に要求しない。
規定どおりの終了と、正常系の解放漏れ・二重解放を区別して記録する。

新ライブラリのC ABIやOS処理は、この分類への追加と、ライブラリ向けL1〜L5の両方で確認する。
まだ未実装のGUI等を、既存コンパイラの合格範囲へ含めない。

## 共通の検証方法と実行構成

証拠は次の種類を分け、互いの代わりにしない。

- 仕様から直接定めた期待値と正常/異常ケース。誤った計算式も、仕様どおりの式として実行することを確認。
- 実行器間・最適化前後の差分比較。AST/IR/native/jwcが同じ誤りを持つ可能性も別に確認。
- 生成入力・変異・固定攻撃。型エラー、不正変換への到達、正常に比較できた入力を別集計。
- sanitizer・LLVM verifier・命令監査。検出器へ意図的な欠陥を入れる負例と、実装への機能試験を分離。
- Leanのモデル内の証明、およびモデルと実装・各変換とのrefinement。モデルの定理数だけで接続の証明数を代用しない。

独立した仕様の期待値がないケースを「複数実行器が一致したから仕様に正しい」と判定しない。
将来の形式評価器の結果や、実装から転記していない期待値を併用する。
検査削除・型誤判定・サイズ計算・二重効果等の欠陥を意図的に入れ、対応する検証が失敗することも確認する。

| 軸 | 実行・記録する構成 |
|---|---|
| 実行器 | Rust AST、Rust IR、Rust版生成native、jwc生成native |
| 解析 | 検査省略あり/なし。debugのassertだけに依存せずreleaseも確認 |
| 最適化 | -O1、-O2+LTOの既存構成を維持し、-O0等は必要な比較条件とともに追加。全構成を既に実行済みとは扱わない |
| プラットフォーム | Linux/Windows x64。OS、clang/LLVM版、ターゲットABI、linker、runtimeの指紋を記録 |
| 計装 | ASan/UBSan/MSan/TSanと対応する負例。OSと依存ライブラリの計装範囲を明示 |
| 自己ホスト | Rust版→jwcの各bootstrap段階で型/IR/LLVMと実行結果を照合。必要な正規化を固定し、異なる生成物を無条件に同一扱いしない |
| 失敗 | 制御された確保/再確保/スレッド作成/リンク等の失敗。実環境を無制限に枯渇させず隔離プロセスと上限を使う |

大きな直積の全セルを常時実行することは求めず、各課題で必須の構成と周期を明記する。
ただし、実行していないセルを「他の構成で通った」ことによって合格へ埋めない。

## 状態と合格の記録

実用テスト1〜12の記録と、[形式証明専用のF1〜F5・証明記録](formal-verification.md) を分ける。
以下は共通の追跡情報。形式証明では専用テンプレートで命題・前提・実際の公理依存・実装との対応まで記録する。
実用テストの合格とLeanのモデル内証明を合算して、5保証全体の完了とは判定しない。

各課題は、少なくとも次の情報を一緒に記録して判定する。

```text
課題ID / 対象となる仕様と機能 / 実装SHA / テスト・定理名
期待する観測結果または定理の文 / 対象構成と仮定 / 失敗注入・負例
生成seedと入力数 / 到達・比較・型エラー・skip・timeoutの内訳
実行ログまたはActions run/job / 実行試験の状態 / 形式証明と実装接続の状態
未完了事項 / 合格条件を狭めた場合の理由と範囲
```

テストの状態は「成功/失敗/未実行/skip/条件不足」を分ける。
証明の状態は「未形式化/モデル内の部分証明/実装との接続待ち/対象範囲で接続済み」を別欄で記録する。
ツール・ヘッダー・sanitizer・DB等が不足する失敗を言語エラーや意味比較の不一致へ分類しない。
今回のローカル環境では、Lean同梱のclangをRust/native試験が拾わないよう、検証器ごとにPATHを分ける。

既存robustの「3秒で時間切れでもクラッシュなしとして許容」は、その限定基準の記録として維持する。
意味比較・回収完了・資源制御・正常終了の試験では、時間切れを成功としない。
意図した規定エラーで止まる攻撃ケースは成功になり得るが、型検査等で目的の操作に届かなければ未検証とする。

「全項目クリア」と報告する際は、既存1〜7、退役の追加試験、8/9、コンパイラの1〜12、詳細23課題、5保証のどの集合かを明記する。
5保証についての完了は、対象とする全言語機能・実行構成の必要な課題に未完了がなく、
形式証明と実装の対応、および信頼する外部部分と仮定が明示された場合に限る。
