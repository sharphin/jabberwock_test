# Jabberwock 言語安全性契約（v2）

更新日: 2026-10-28

状態: **安全性の受入基準と、jwc版を基準にした基本言語の完成条件を確定。個々の合否は対象版の検証結果に記録する。**

この文書は、Jabberwock が言語機能として守る性質、プロジェクトとして安全性を受け入れる基準、アプリケーション開発者の責任範囲を定める。

## 安全性の受入基準

**定めた言語仕様・対象条件の下で、合意した全テストの合格をもって「言語全体の安全性に合格」と判定する。** これが本プロジェクトで用いる安全性の受入基準である。

- 判断には言語仕様、実装、既存の解析・検証・テスト結果を用いる。
- 対象は、定義した条件の下で到達可能な実行における安全性違反。危険になり得る表現や状態が存在すること自体を違反とはしない。
- 寿命後のrefの保持、複数のref mutの共存、仕様で定めたエラー停止などは、必要な保護条件が守られていれば、それ自体は違反ではない。
- 到達不能を理由に対象外とする場合は、仕様と実装上の根拠を確認する。単なる宣言や未実行を根拠に除外しない。
- 対象外の環境や、実際の対象実行に現れないあらゆる潜在危険の不存在まで、完成条件として要求しない。
- 合意した基準へ、別の無制限な証明要求を勝手に追加しない。

### 対象と合否の記録

1. 判定対象のソース版、コンパイラ、OS、ビルド・実行条件を明記する。
2. 既存基盤のコンパイラ別12項目と最終5目標の検証を対象とする。5目標は、意味保存、メモリ安全性、型安全性、所有権・参照の整合性、実行時チェックの正しさ。
3. 実用検査と形式検証は既存の別ツールで実行し、各工程について定めた合格・正常完走の条件を確認する。
4. 必須検査の失敗、未実行、欠落、検証器の故障が残れば、全テスト合格とはしない。
5. jwcとRust、WindowsとLinuxの結果を分離する。他方の結果を転用せず、合格の表明にも確認した対象を添える。
6. 各ツールの出力値は改変せずに記録する。例えば、工程の正常完走や `PROBES_PASS_ONLY` はその範囲の結果として集約し、単独で全項目の合格とはしない。

形式検証で得られた個別命題の証明状況も記録する。`NOT_PROVEN` はその命題の状態を表し、検証器の故障とは区別する。個別命題の未証明を理由に、合意していない追加証明を基本言語の完成条件へ自動追加しない。必須工程の検証失敗を無視することは認めない。

## 基本言語の完成条件

**jwc版について、対象仕様の実装と、上記の全テスト合格を確認できれば、基本言語は完成と判断する。** 今後の開発と受入判断はjwc版を中心に進める。

Rust版は比較・構築に用いる別実装として結果を管理する。Rust版インタプリタのAST解析とjwc版のIR解析で省略可能な範囲が異なること自体は、jwc版の完成を妨げる条件にしない。両コンパイラで共通とする仕様・挙動は、既存の比較検査で確認する。

本契約による合格は、Rustとの安全水準の比較評価を実施・完了したという意味ではない。他言語との比較の有無を、本契約の完成条件に追加しない。

完成後は標準ライブラリなどの実装へ進み、変更に応じて既存の安全性検査を継続する。仕様・対象条件が変わる場合は、影響する検証範囲も更新する。

## 原則

1. 利用者にメモリ安全性を破る `unsafe` 相当の脱出口を提供しない。証明または検査で安全性を確認できず、信頼できる境界契約も存在しない操作は拒否する。
2. 安全性はプログラマの自己申告ではなく、型規則、静的証明、必要な実行時検査、および明示した信頼境界によって担保する。
3. 最適化は安全性を弱めてはならない。実行時検査の省略には、対象アクセスでの有効性を裏付ける証明が必要である。
4. 言語の汎用性・性能は目標だが、安全性の例外をユーザーに公開して達成するものではない。
5. 保証は**対象と前提を伴う**。外部ABI、OS、アロケータ、Cランタイム、コンパイラのバックエンド、ハードウェアなど、信頼境界の内外を明示する。

## 言語としての保証目標（現時点では未達成項目を含む）

- **メモリ安全性:** 不正な参照外し、use-after-free、double-free、範囲外の読み書き、未初期化領域の不正使用を起こさせない。拒否はコンパイルエラーまたは仕様化された実行時エラーとする。
- **所有権・借用・参照:** 一意所有、移動後の旧所有者利用禁止、借用先の無効化、世代付き参照の有効性を守る。
- **型と演算:** 型付けされた操作のメモリ表現との整合性を維持し、整数オーバーフロー・ゼロ除算などは言語仕様で挙動を規定する。未規定の挙動を「安全」と見なさない。
- **並行性:** データ競合を許さないことを目標とするが、実際に保証できる範囲は並行処理機能の仕様・実装・検証後に確定する。
- **コンパイル/実行の全経路:** インタプリタ、Rust製コンパイラ、セルフホスト版、生成コード、ランタイム、最適化を跨いで対象の保証が保持されることを目標とする。
- **外部境界:** FFI、OS・デバイス操作などで検証不能な性質を黙って内部保証へ取り込まない。公開APIを安全にするために必要な隔離・権限・前提は個別仕様で定義する。

上記の保証目標はアプリケーションが終了すること、資源が枯渇しないこと、すべての実行が成功することを意味しない。

## 言語が保証しないもの

- アプリケーションの業務ロジックの正しさ、金銭処理の正当性、意図した結果
- 認証・認可・アクセス制御ポリシーの正しさ
- SQLインジェクション、XSS、SSRFなどの**アプリケーション・プロトコル固有の脆弱性**が生じないこと
- 個人情報・秘密情報の扱いに関するアプリケーション固有の方針の妥当性
- デッドロック不在、サービス可用性、リアルタイム性、サイドチャネル耐性など、別途仕様と証明が必要な性質

標準ライブラリがこれらの対策を支援しても、アプリケーション固有の正しさが自動で保証されるわけではない。

## 形式検証における証拠の分類

以下は形式検証ツールが扱う証拠の意味を記録するものであり、上記のプロジェクト受入基準を別の基準に置き換えるものではない。未証明の命題を証明済みと表示しない。

| 分類 | 意味 | 全体の証明と見なすか |
| --- | --- | --- |
| `MODEL_PROVEN` | Leanが抽象モデル内の性質を証明 | いいえ |
| `CONDITIONAL_PROVEN` | 明示された前提の下でLeanが証明 | いいえ |
| `STRUCTURE_MATCHED` | 生産実装のソース形状が期待パターンと一致 | いいえ |
| `REFINEMENT_PROVEN` | 実装と抽象モデルの意味論的な対応を証明 | 当該境界のみ |
| `END_TO_END_PROVEN` | 対象経路と信頼前提を列挙して生成コードまで証明 | 対象性質についてのみ |
| `NOT_PROVEN` | 必要な証拠が不足 | いいえ |

## 個別の形式証明で管理する事項

以下は既存の形式検証が管理する命題の記録。実際の到達状況は対象版のレポートで確認し、この一覧を基本言語の完成に必要な追加作業へ自動的に読み替えない。

- `formal/JabberwockFormal/Ownership.lean` の所有権モデルと実メモリ配置・解放の対応
- `formal/JabberwockFormal/Generation.lean` の世代管理と実ランタイムの対応
- `formal/JabberwockFormal/ElisionDecision.lean` の `FactSoundAtAccess`（解析事実が実アクセス時の生存・世代の有効性を保証すること）
- 最適化/LLVM生成/外部ランタイムを通過したメモリ安全性の保存
- 到達済みCFGでの一般的な変更回数上限と動的ワークリストの停止性

`scripts/formal_tool.py` の `FINAL: NOT_PROVEN` は、そのツールが対象とする形式証明の結果として記録する。基盤の正常完走、個別命題の証明結果、プロジェクトの受入判定をそれぞれ記録する。

## 個別の形式証明を拡充する場合の順序

以下は追加の形式証明を実施すると決めた場合の整理であり、合意済みの完成条件への追加要求ではない。

1. **安全性仕様と信頼境界:** 言語の操作的意味論、メモリ表現、外部依存の契約を明確化。
2. **メモリモデルと実装の対応:** 所有権移動、解放、世代無効化、読み書きについて、一段階ずつ精密化証明を作る。
3. **検査省略の健全性:** `FactSoundAtAccess` を実際のCFGデータフロー、アクセスの妥当性へ結び付ける。
4. **CFG解析の停止性:** `changeCount ≤ n` と再登録の有限性を証明し、解析の完了を裏付ける。
5. **エンドツーエンド:** ソースから出力コードまでの意味保存と、列挙された信頼境界を接続する。

**判定ルール:** プロジェクトの安全性の合否は本契約の受入基準で報告する。個別の形式証明結果とアプリケーション固有の正しさは、それぞれの対象に対応付けて記録する。
