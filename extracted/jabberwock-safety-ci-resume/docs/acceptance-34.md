> **開発上の完成条件との区別:** 本書の34件は「検証対象のJabberwockコンパイラの数学的・実証的受入基準」であり、**形式証明テストツールの実装完成率を表すものではない**。34件が未達でも検証ツールは機能として実装完了し得る。ツールの完成条件・能力別進捗・テスト実施状況は `docs/formal-tool-completion.md` と `scripts/tool_implementation_progress.py` で独立管理する。既存のNOT_PROVEN判定や受入監査の厳格さは変更しない。

# Jabberwock: 34件の正式受入基準と証拠の境界

## 対象と判定

検査対象は **jwc（セルフホスト処理系）** と **Rust製Jabberwock処理系** の2系統。
各系統で安全性12項目（S01〜S12）、全体の数学的証明G1〜G5（意味保存、
メモリ安全性、型安全性、所有権・参照の整合性、実行時チェック）を個別に扱う。
合計は **24件の実証項目と10件の数学的証明項目＝34件**。

詳細な規範文は `scripts/acceptance_requirements.py` の
`ITEM_CRITERIA` と `GOAL_CRITERIA` に置いた。
これは必要条件の定義であり、合格宣言ではない。

**有限の実行例だけでは、プログラム全体に関する普遍的安全性や意味保存を
数学的に証明できない。**
実証で証拠が集まっても、対象と前提条件を明記した上で形式的な議論と
処理系への対応証明が別途必要である。

| S03 | 競合・同期・回収の不変条件 | 並行性モデルとの対応・検出器 |
| S04 | LLVMのUB、poison/undef、alias、lifetime規則 | LLVM生成全経路の証明 |
| S05 | 全最適化・LTO構成で意味とチェック保存 | 最適化変換の仕様対応 |
| S06 | 未初期化値を読む到達可能経路がない | 生成コード初期化保証 |
| S07 | stage2/3でも安全性と5目標を再検査 | 自己ホスト連鎖の証拠 |
| S08 | 確保失敗・スタック/スレッド/OS資源失敗の安全な停止 | 故障注入と資源モデルの全範囲 |

## 現在のLean証明の範囲

- `formal/JabberwockFormal/Generation.lean`: 世代の単調性、
  退役後の非復活、抽象アクセスゲート、無効化後の有限状態遷移を経た\n  読み出し・書き込み成功の否定など。
- `formal/JabberwockFormal/Ownership.lean`: 所有位置の抽象モデル、
  `checkedMove`の一意性保存など。
- `formal/JabberwockFormal/Jwc/ReferenceAccess.lean` および
  `Rust/ReferenceAccess.lean`: 両コンパイラ固有の抽象世代ゲート・読書き・moveについて
  局所的な定理。
- `formal/compilers/{jwc,rust}/obligations.json`: 各Gの定理名、
  仮定・除外・コンパイラソースとのハッシュ対応。

### G1〜G5を同時に形式化した限定カーネル

`formal/JabberwockFormal/ScopedGoals.lean` を追加。
自然数定数・加算・世代を検査する読み取りからなる**型付きの小言語**と、
それに対応する独立したターゲット命令木を定義した。

- G1: 小言語からターゲット命令木へのloweringが正常値／dangling失敗の観測結果を保存する定理
- G2: 正常に完了する世代付き読み出しは、世代一致かつ非退役の条件を満たす定理
- G3: この小言語の型付き式をloweringしても、ターゲット命令木の型の整合性を保つ定理
- G4: 抽象的な`checkedMove`が、開始時の所有者一意性を正常終了後にも保存する定理
- G5: LLVM世代チェックのBoolean条件と有効な世代の同値定理

両エミッタのBooleanゲート同値定理を合わせて登録した。
`JabberwockFormal.lean` からimportし、一括検査のLeanビルド対象にする。

**証明範囲はこの小言語だけ。** 型付き小言語をJabberwockの全構文・全型・全IR・
最適化・LLVMコード・Cランタイムに同一視してはならない。
特に`Nat`加算は機械整数オーバーフローをモデル化しておらず、
`checkedLoad`はアドレスの生存性や並行atomicの意味論をモデル化していない。
型検査器・パス・FFI・並行実行の実装との正式な対応証明は引き続き未完成。
Lean 4.24.0のビルド／定理チェックも実機実行担当が確認するまで未検証。

### LLVM世代チェックの部分的な実装対応（今回追加）

`formal/JabberwockFormal/EmittedGate.lean` は、次の3命令からなる
Boolean判定部分をLeanで形式化する。

```llvm
%different = icmp ne i64 %current, %saved
%retired = icmp eq i64 %current, -1
%bad = or i1 %different, %retired
```

この条件の否定が「参照の世代が一致し、退役マーカーではない」と
同値であること、および両処理系の既存の局所モデルが同じ条件に対応することを
定理として記述した。

`scripts/proof_emitter_correspondence.py` は実際の
`jwc/llvm.jw` と `src/ir/llvm.rs` の該当エミッタ関数を読み、
原子的load、分岐、退役検査、失敗時のtrapの命令テンプレートを照合する。
条件式の変化や分岐反転などに対する負例テストも用意した。
ローカル一括コマンドからこの検査も起動する。

ただしこの照合は**ソーステンプレートの構造チェック**であり、
LLVMの正式な意味論に基づいた実行コードとの対応証明ではない。
分岐生成ヘルパー、ポインタの生存期間、失敗関数の終了性、
LLVM poison/undef、最適化、全実行経路の健全性はまだ対象外。
G1〜G5の全体証明には昇格させない。

**未完成**なのは、これらの抽象定理が実際のJabberwockの型検査、
コンパイラ中間表現、LLVM生成、最適化・リンク、Cランタイム、FFI、実機動作に
どのように対応するかを証明する部分である。
ハッシュの一致は「同じソースを参照した」ことの証拠に過ぎず、
**仕様との意味的同値性の証明にはならない**。

## 形式証明の実装順序

1. 対象言語の操作的意味論、型付け規則、所有権規則、規定の安全な停止をLeanに定義。
2. 生成前IRと型付きAST間の関係、および型保存・進行を証明（G3）。
3. 世代/借用/回収の全遷移をCランタイムに対応させ、並行性とFFIの仮定を明示（G2・G4）。
4. チェック挿入／省略の変換とLLVM上での意味を定義し健全性を証明（G5）。
5. 各パスの意味保存を合成し、入出力・エラー・外部副作用の観測的等価性を証明（G1）。
6. 1〜5をjwcとRust製処理系それぞれの**現在のソース**に対応づける。モデルだけの定理流用はしない。
7. 定理から使用した公理・除外を監査し、未証明または未モデル化の機能は正式受入に含めない。

## Windowsで1コマンドの全テスト

リポジトリ直下のPowerShellで次の**1行**を実行する。

```powershell
py scripts/verify_all_local.py
```

この引数なしの入口は `scripts/run_everything.py` に接続されており、次の7工程をすべて実行する。
**Python回帰テスト、Windows安全性プローブ全件、実装LLVMエミッタとの局所対応照合、Leanの抽象モデルと両コンパイラの全証明監査、
34件の証拠監査、21ケース×4者のベンチマーク、旧Rust製コンパイラの検査数監視**。
後続の工程は先行工程が失敗しても可能な限り実行される。
ログと終了コードを `target/verification-complete/` に保存し、
`summary.json` が工程ごとの結果、`acceptance-34.json` が受入条件ごとの未達要因となる。

このコマンドはすべての失敗を成功として隠さない。
**現時点ではG1〜G5の実コンパイラ全体に対する数学的対応証明が欠けるため、
34件の正式受入は未成立で、全工程の実行が成功しても最終EXIT 0とはならない**。
「コマンド一発で全検査を起動する」ことと
「34件の数学的・実証的完全性がすでに成立している」ことは区別する。

## ユーザーが実行する確認と、コード側の事前準備

**実行確認はユーザー担当。** GitHub Actionsには依存しない。
Windowsの入口は次のとおり（PowerShell、リポジトリ直下）:

```powershell
py scripts/verify_all_local.py
py -m unittest discover -s scripts -p "test_*.py"
```

既にユーザーが作成したレポートのみに対して34件を監査する場合:

```powershell
py scripts/acceptance_report.py --practical target/safety-windows-report.json --formal target/formal-report.json --inventory target/whole-proof-inventory.json --os windows
```

監査出力は `target/local-verification.json` 内の `acceptance_34`、
あるいは単独実行時の `target/acceptance-34.json`。
ソース・テスト入力・Lean定理とその依存先・マニフェストの識別情報、\n実行予定と実行済みのプローブ一覧、個別プローブの終了コード、
5件ずつの実証目標、数・コンパイラ帰属が一致しない場合は証拠を拒否する。

**現時点では34件を受入済みと報告できない**ため、監査結果は
`NOT_ACCEPTED` または `INVALID_EVIDENCE`。
未証明を`PASS`と書き換えて解決したことにはしない。

受入基準の拡充・ケース追加は可能。ケース数を固定値だけで照合して
新規ケースの検査漏れを正当化してはならない。


## 実装ソースからの証明義務と受入判定の接続

`scripts/whole_compiler_proof.py` は jwc/Rust と runtime の実装ソースから、
各ソースとG1〜G5の対応証明義務を生成する。
`acceptance_report.py` は `--inventory` を必須とし、正規のソース一覧・フェーズ・目標・ハッシュと一致しない結果を拒否する。
G1〜G5それぞれに未証明の実装リンクを列挙する。
ソース一覧の一致は意味保存や型安全性の数学的証明ではないため、未解決のrefinementを正式受入済みに変更しない。

## 実機での検証→報告→修正サイクル

Windows PowerShellで、PRの最新headを取得後、リポジトリ直下から次を実行する。

```powershell
py scripts/verify_all_local.py
py scripts/package_verification.py
```

`verify_all_local.py` の終了コードが1であっても、未証明の数学的義務による最終受入未達と、テストの失敗を混同しない。`target/verification-complete/summary.json` の `stages` に工程別終了コード、`evidence` に未証明項目とテスト失敗内容を記録する。証明義務の一覧生成が正常完了した場合、義務が未証明でも一覧生成ステージ自体は終了コード0とする。全体受入が成立しなければ最終終了コードは0にしない。

`target/verification-evidence.zip` はレポートJSONとstdout/stderrログをまとめた再レビュー用アーカイブ。ZIP内部の `evidence-manifest.json` に各ファイルのSHA-256を記録する。テスト結果の真正性や数学的正しさの証明にはならない。**共有前にログ内のローカルパス、認証情報、秘密情報を確認すること。**

この段階では全コンパイラ対応証明の検証器、ビルド依存閉包の完全検証、LLVM意味論との接続は未実装である。受入監査はその状態を`NOT_ACCEPTED`と報告し続ける。コンパイラ実装には手を加えない。

## 追加した独立監査工程（未証明を明確化）

- `scripts/build_dependency_audit.py`: jwcの静的`use`依存、Rustの宣言的`mod`・リテラル`include!`とCargoの明示的依存宣言を監査し、欠落・解決不能を`BLOCKED`として報告する。結果の`DECLARED_CLOSURE_CHECKED`はビルド全入力の閉包証明を意味しない。
- `scripts/llvm_ir_audit.py`: ベンチマークのコンパイル工程で実際に生成した`.ll`をLLVM `opt -passes=verify`へ渡す。`IR_WELL_FORMED`はLLVM IRとしての妥当性の一部であり、未定義動作の不在や意味保存の数学的証明ではない。
- `scripts/run_everything.py`: 上記工程の独立終了コードとレポートを保存。単なるソーステンプレート一致を形式証明完了として扱わない。

**未完了の本質的課題:** 動的・生成済みビルド入力とツールチェーンの完全な実行依存閉包、LLVMの正式な意味論に対するプログラム全体のrefinement、Leanの実装対応定理によって正当化された証明状態遷移。これらが残る限り正式受入は成立しない。
