# 安全の確かめ方と、まだ確かめていないこと

jabberwock の安全は「設計」と「実装」の 2 段で考える。

- **設計**: ref は使うたびに世代を比べる。検査を消すのは、静的解析が「消してよい」と証明できたときだけ。
  添字はいつも範囲を調べる。なので決まりどおりに動けば、解放後の使用・範囲外の読み書きは起きない。
- **実装**: 決まりどおりに作れているか。これはテストで「試した範囲では壊れなかった」としか言えない
  （Rust や Go も同じで、実装の穴は今も見つかっている）。

この文書は、実装をどこまで確かめたかと、まだ確かめていないことの一覧。確かめた範囲を広げたら、ここを直す。

項目1〜7の追加検証・合格条件・LLVMのアドレス計算の確認は [safety-validation.md](safety-validation.md) に記録する。
項目1〜7は定めた検証基準を満たした。根拠となる実装とCI実行は追加文書を参照する。
5つの保証目標についての全体の検証体系と既存1〜9の位置づけは [verification-plan.md](verification-plan.md)。
この一覧の1〜9だけで、言語・実装全体の5目標を保証済みとは扱わない。
2026-10-26の退役実装、1〜9の再検証と実行基盤の制約は [generation-retirement.md](generation-retirement.md)。

## 現在の一覧は12項目

2026-10-26、現行コンパイラの改良・ライブラリ実装を進めるための実用上の確認として、1〜9に次の3項目を追加した。
形式証明の完成とは別の判定である。5領域との対応と具体的な合格条件は [実用上の安全確認](verification-plan.md#実用上の安全確認) を参照する。

| 項目 | 追加して確認する内容 | 状態 |
|---|---|---|
| 10. 仕様どおりの動作・型検査・副作用 | 独立した期待値で正常系・拒否系、型/権限、評価順、外部I/Oの回数と順序を確認する | 既存試験あり。debug CLIの副作用二重実行を再確認。項目全体は未合格 |
| 11. 所有権・資源回収・途中失敗 | ムーブ・退役・送受信・各制御フロー・途中失敗で、参照と必要な回収が仕様に一致する | 退役等の既存試験は成功。追加の経路対応と失敗注入は未完 |
| 12. 実際に使う構成での検証 | コンパイラ自身のdebug/release、Linux/Windows、Rust/jwc生成物、ABI/リンク、計装の実動作を確認する | 未実行構成あり。生成nativeの-O2成功だけでRust releaseを合格としない |

合格すれば、5領域すべてについて「対象の機能・環境で定めた実用試験を通過した」と判断する構成。
対象外の機能・未実装ライブラリへ合格を広げない。既存1〜9の結果と新設10〜12の状態も分けて報告する。
ライブラリ向けの旧10〜14は [作業メモ](safety-ci-handoff.md) でL1〜L5へ改称し、コンパイラの番号と区別する。
形式証明は [専用のF1〜F5と記録様式](formal-verification.md) で進め、実用テストの成功数へ加えない。
追加したrelease実行と副作用検査の結果は [実用テストの追加実行](practical-retest.md)。未合格の項目もそのまま記録する。

## 確かめていること（2026-10-25）

| テスト | 何を見るか |
|---|---|
| ふつうのテスト（`cargo test`） | interp と IR を全テストで突き合わせる。デバッグビルドでは、消した検査も `debug_assert!` で確かめる |
| `JW_NATIVE=1 cargo test` | 全テストを実行ファイルでも突き合わせる（出力・エラーの文と位置・残った区画の数） |
| `tests/fuzz.rs` | 型の通るプログラムを自動で作り、interp と実行ファイルで比べる（`JW_FUZZ=本数`） |
| `tests/analyze.rs` | 検査を消してよい例と、消してはいけない例 |
| `tests/robust.rs` の `hostile_inputs_do_not_crash` | 極端な入力約 50 本（深い入れ子・長い式・巨大な数・巨大な配列やリスト・長い名前など）で、処理系が落ちない |
| `tests/robust.rs` の `mutated_programs_do_not_crash` | 例とテストのプログラムを壊したもの（ふつう 150 本、`JW_ROBUST=本数`）で落ちない |
| `tests/robust.rs` の `memory_attacks_stop_with_an_error` | メモリ破壊・情報漏洩を狙うプログラム 16 本が、interp・解析なし・実行ファイルで必ずエラーで止まり、隠した値を出さない |
| `JW_ROBUST_ASAN=1` | 上の実行ファイルを ASan（メモリの壊れ）と UBSan（C の未定義の動き）つきで作る。例のプログラムもすべて流す |
| `tests/robust.rs` の `generated_code_guards_undefined_operations` | 書き出した LLVM の割り算・ずらしの前に、0 / -1 / 幅以上を避ける守りがあるか（UBSan の代わり。llvm.rs の守りの形を見る） |
| `JW_CFLAGS=-fsanitize=...` | `JW_NATIVE=1` や fuzz.rs の実行ファイルを sanitizer つきで作る。address / thread / memory は書き出した関数にも印を付ける（native.rs の `instrument`） |

「落ちる」は、panic・スタックあふれ・内部エラー・シグナルでの終了。時間切れ（3 秒）は合格にしている。

### これまでに見つけて直したもの

- 括弧などの深い入れ子でスタックがあふれる → 256 段までにした（外部レビュー）
- `"abc".repeat(巨大な数)` で panic → 確保の前に長さを確かめる（外部レビュー）
- `[0; 巨大な数]` の配列で panic・スタックあふれ → 配列は 1 MiB まで
- `1 + 1 + …`（1 万個）や `.abs()` の長い鎖でスタックあふれ → 鎖も入れ子として数える（robust.rs で発見）
- `[0; 9兆]` のリストで interp が確保に失敗して落ちる → 「メモリが足りません」のエラー（robust.rs で発見）

ASan/UBSan をつけた実行では、メモリの壊れと未定義の動きは見つかっていない。

## 自動で流す仕組み（.github/workflows/safety.yml）

push と PR では短く、毎晩（日本時間 3:00）は 20 倍の本数で流す。手で動かすときは `scale` で倍率を決める。種は実行の番号で毎回変える。
落ちたら、入力を `dump-*` として残す。

| 仕事 | 中身 | 下の項目 |
|---|---|---|
| robust | 堅牢性テスト全部を ASan/UBSan つきで。push と毎晩は、壊したプログラムも実行ファイルで動かす | 2・4・8 |
| fuzz-asan | fuzz.rs を ASan/UBSan つきで、-O1 と -O2・LTO。push と毎晩は全テストを ASan/UBSan の実行ファイルで突き合わせる | 1・5 |
| tsan | スレッドと実行ファイルのテストを TSan つきで（倍率の回数くり返す） | 3 |
| msan | 全テストを MSan つきの実行ファイルで突き合わせる | 6 |
| jwc・jwc-msan | jwc生成LLVMをASan/UBSan・MSanで計装し、解析あり／なしのRust版と比較 | 6・7 |

## 項目1〜7の検証完了と残る課題

2026-10-25、実装 `691f8d6` で以下の検証基準をすべて満たし、最終CIも成功した。
具体的な本数・構成・負例・LLVMのアドレス計算の確認は [safety-validation.md](safety-validation.md) に記録した。

| 項目 | 検証結果 |
|---|---|
| 1. 検査を消す解析 | 解析あり／なしのAST・IR・ネイティブ比較が成功 |
| 2. 型の通る攻撃 | 78件すべてが操作に到達し、期待する診断で停止。型エラーによるスキップなし |
| 3. データ競合 | 共有フラグと世代番号の競合を再現・修正。TSanの負例と43件×3回の試験が成功 |
| 4. 生成LLVMの未定義動作 | 除算・シフトの守り、390モジュールの監査とverifier、アドレスと演算の端の実行試験が成功 |
| 5. 最適化 | -O1と-O2＋LTOのsanitizer付き比較が成功 |
| 6. 未初期化メモリ | C呼び出し境界の検出漏れも修正し、負例・MSan全体358件が成功 |
| 7. 自己ホスト版 | jwc生成LLVMをASan/UBSan・MSanで実際に計装し、全攻撃・演算の端・生成入力の比較が成功 |

これは定めた機能・構成での検証完了の判定であり、あらゆる入力の数学的な証明ではない。
CIで固定攻撃・負例・生成入力の検証を継続する。以下は別の課題として残る。

8. **メモリを使い切ったとき**。interp は「メモリが足りません」のエラー、実行ファイルは内部エラーで止まり、表示がそろっていない。
   メモリの上限そのものも決めていない。無限ループは時間切れで合格にしている。
9. **配列の大きさの数え漏れ**。ジェネリックな構造体の型の引数に大きな配列を入れると、1 MiB の上限を通り抜けることがある（あとで直す）。

### メモリの安全とは別の話

- `read_file` / `write_file` / `run_command` は何でもできる。他人のコードを動かすなら、言語の外で囲う仕組み（サンドボックス）が要る。
- 時間とメモリを使い切らせる攻撃（無限ループ・巨大な確保）は、言語の中では止めない。

## 動かし方

```
cargo test --test robust                      # ふだん（20 秒ほど）
JW_ROBUST=20000 cargo test --test robust      # 変異を増やす（JW_ROBUST_SEED で始めの種）
JW_ROBUST_NATIVE=1 cargo test --test robust   # 変異も実行ファイルで動かす
JW_ROBUST_ASAN=1 cargo test --test robust     # ASan / UBSan つき（clang の実行時ライブラリが要る）
JW_ROBUST_DUMP=フォルダ                        # 落ちた入力をファイルに残す
JW_NATIVE=1 JW_CFLAGS="-fsanitize=thread" cargo test --test threads   # TSan（MSan は -fsanitize=memory）
```

落ち方を見つけて直したら、`tests/robust.rs` の `hostile` に入力を足し、上の「見つけて直したもの」に書く。
